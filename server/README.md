# Server

## How it works

- One Node process (Express + `ws`) serves the built client from `build/`, runs the game over WebSockets on the same port, stores player data in SQLite (`node:sqlite`), and simulates every synced NPC on a headless Rapier world.
- It is bundled by [build.mjs](build.mjs) — THE build, shared by `npm run build`, `npm run dev` (watch) and `npm test` (which bundles `tests/` to `dist-test/` and runs `node --test`). It imports the client's modules from `src/` — protocol, actor specs and state machines, the height pipeline, the movement resolver, and the CONTENT TREES each world is written as — so behavior is written once. The client never imports `server/`.
- The build replaces three.js and R3F with a stub, because the trees' views import them and the server only ever READS the tree, never renders it. `three` stays external, so a real leak fails the boot. → [DECISIONS.md](DECISIONS.md)
- [src/index.ts](src/index.ts): boot order — database check, physics world (with its generation worker), HTTP, WebSocket transport, the world tick (`TICK_HZ`/`TICK_MS`/`TICK_SECONDS` in [game/constants.ts](src/game/constants.ts)) and the save sweep, flush on shutdown.
- [src/transport/](src/transport): [index.ts](src/transport/index.ts) — `createApp` (static client plus a catch-all for the fake URL paths) and `attachWebSocketTransport` (sockets, ping/pong reaper, `routeToWorld`: every validated message becomes one `World` call; implements `Outbox`, permessage-deflate on every frame (`PER_MESSAGE_DEFLATE` in [constants.ts](src/transport/constants.ts), context kept across frames; `WS_DEFLATE=off` disables it), and with it off, corking each socket so a tick's frames leave as one write); frame validation (`parseClientMessage`) in [utils.ts](src/transport/utils.ts).
- [src/game/world.ts](src/game/world.ts): `World` — sessions, one room per domain, presence, player data, the intro's host claims (`host`: [DECISIONS.md](DECISIONS.md) "Hosts"), and the entity calls it forwards to the `EntityManager`; talks only through `Outbox` ([game/types.ts](src/game/types.ts)).
- [src/game/PlayerPersistence.ts](src/game/PlayerPersistence.ts): `PlayerPersistence` — one record per identity, saves on last disconnect or every `SAVE_INTERVAL_MS` if dirty, `saveAll` on shutdown; it accepts a patch through `validatePatch` ([game/utils.ts](src/game/utils.ts)).
- [src/data/](src/data): all SQL — [index.ts](src/data/index.ts) (open, schema version, `runMigrations`), the append-only `MIGRATIONS` in [registry.ts](src/data/registry.ts), the player queries in [store.ts](src/data/store.ts).
- [src/game/entities/](src/game/entities): [EntityManager.ts](src/game/entities/EntityManager.ts), the NPC authority. Clients register what they render; kinds from `ACTOR_CATALOG` run their own client state machine here with the nearest player as "the player". [utils.ts](src/game/entities/utils.ts): `publishTick` sends changed fields as server-time-stamped snapshots (positions as the shortest decimal of their float32, `ry` to 1e-4); `clipDurationsOf` reads each kind's clip lengths.
- [src/game/physics/](src/game/physics): [physicsWorld.ts](src/game/physics/physicsWorld.ts) (the Rapier world for `PHYSICS_DOMAIN`, one refcounted [ChunkStore](src/game/physics/ChunkStore.ts) per chunk layer — terrain, dressing — on a budgeted [JobQueue](src/game/physics/JobQueue.ts)), [chunkGenerator.ts](src/game/physics/chunkGenerator.ts) + [chunkGenerator.worker.ts](src/game/physics/chunkGenerator.worker.ts) (`ChunkGenerator`: the server boot samples each layer's Rapier-free data on a worker thread and the queue only makes the bodies; a dead worker, a failed job, tests, tools and `CHUNK_GENERATOR=inline` build in place; it also answers the bodies' analytic height queries, `PhysicsWorld.heightAt`, so a cold area never blocks a tick), [utils.ts](src/game/physics/utils.ts) (the Rapier-free samplers: heightfield samples identical to the client's, the dressing obstacle points from `DRESSING_COLLIDER_SPECS`, the tunnel chunks).
- [src/game/physics/bodies/](src/game/physics/bodies): [index.ts](src/game/physics/bodies/index.ts) (dressing obstacle bodies from those points, sealed building hulls and door positions, and `createNpcBody`, which picks [GroundBody](src/game/physics/bodies/GroundBody.ts) or [FreeBody](src/game/physics/bodies/FreeBody.ts) by the spec's `movement`), [Walker.ts](src/game/physics/bodies/Walker.ts) (a capsule on the shared movement resolver), [PlayerBodies.ts](src/game/physics/bodies/PlayerBodies.ts) (a capsule per player).
- [src/cli/](src/cli): `db:migrate`, `db:inspect`, and `physics:demo` (with the terrain scans in [utils.ts](src/cli/utils.ts), which the physics tests share).
- Ops runbook: root [README.md](../README.md#server-database-deploy). NPC sync: [NPC_TRACKING.md](../NPC_TRACKING.md).

## How to add another

- **Synced NPC**: nothing in `server/` — follow "Wiring a NEW NPC" in [NPC_TRACKING.md](../NPC_TRACKING.md); test it headlessly by copying a case in `server/tests/entities.test.ts`.
- **Message type**: see [src/net/README.md](../src/net/README.md). On the server: a case in `parseClientMessage` and one in `routeToWorld` ([src/transport/](src/transport)), and the `World` method it calls.
- **NPC movement kind** (beside `ground`/`free`): a class file `src/game/physics/bodies/<Name>Body.ts` implementing `NpcBody` ([bodies/types.ts](src/game/physics/bodies/types.ts); resolve its pose with `writeResolvedPose`) and a branch in `createNpcBody` ([bodies/index.ts](src/game/physics/bodies/index.ts)), plus the client's branch in `objects/actors/model/hooks.ts`.
- **Chunk layer** (another kind of world collider built per chunk): an entry in `ChunkLayerData` ([types.ts](src/game/physics/types.ts)), its Rapier-free sampler in [utils.ts](src/game/physics/utils.ts) and in the worker's `SAMPLERS`, a `ChunkStore` in `PhysicsWorld`, and a hold in `GroundBody` if walkers need it under them.
- **Database change**:
  1. Append a migration to `MIGRATIONS` ([src/data/registry.ts](src/data/registry.ts)) and put its queries in [src/data/store.ts](src/data/store.ts).
  2. Run `npm run db:migrate` on the live database before deploying.
- **Dressing collider**: nothing in `server/` — give the feature a Three-free spec exporting a `DressingColliderSpec` and add it to `DRESSING_COLLIDER_SPECS` in `src/objects/dressing/registry.ts`.
- **Building variant**: nothing in `server/` — add its spec to `src/objects/actors/building/spec.ts`; the hull follows.
