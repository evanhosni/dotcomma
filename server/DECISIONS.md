# Server, persistence, deploy and entity sync — decisions

> Moved verbatim from CLAUDE.md (Oct 2026) to keep it under the context limit. Section names quoted in the text ("Blending", "Rivers", …) refer to the other decision docs listed in CLAUDE.md under "Where the docs are".

## Multiplayer server, persistence, deploy (Sept 2026)

One Railway service runs `server/` (Node 24, Express + `ws`, `node:sqlite`) and serves the CRA build from `build/`; SQLite lives on a Railway volume. Assets are still in `public/` (the R2 CDN pipeline — Phase 4 of the original plan — is DEFERRED until there are enough assets to warrant a bucket; `REACT_APP_CDN_URL` in `.env.example` is reserved for it). Runtime deps are exactly `express` + `ws`; everything the server shares with the client — Rapier (`@dimforge/rapier3d-compat`, via `@react-three/rapier`), delaunator, noise-ts, seedrandom — is BUNDLED into the server build from the ROOT install, never a second server-side copy. No ORM, no socket library, no state library, no GitHub Actions — each was considered and rejected. Read `README.md` → "Server, database, deploy" for the ops runbook.

The layout of `server/` is in [README.md](README.md) and the client side of the network in [src/net/README.md](../src/net/README.md). The server is BUNDLED (esbuild) and imports the client's Three-free modules straight from `src/` (protocol, specs, state machines, the height pipeline, the domain configs); the CLIENT never imports `server/` (CRA's ModuleScopePlugin forbids it). `game/world.ts` talks to sockets only through an `Outbox` — the ONLY abstraction, kept so Colyseus could replace `ws` later; do not widen it. `railway.json` / `.node-version` / `.npmrc` (`include=dev` — Railway must install devDependencies for craco + tsc) configure the deploy; `scripts/deploy.mjs` is `npm run deploy`.

Rules that came out of building it:
- **Two ids.** `identity` = client uuid in localStorage (persistence key, sent once in `hello`). `id` = server-assigned SESSION id (all presence messages). Two tabs share an identity but are two sessions — that is what makes local two-tab testing possible.
- **Presence is scoped per DOMAIN (rooms), not filtered.** Domain switch = leave(old) + join(new) + fresh `init` to the mover. Phase 6 entity sync must inherit this scoping.
- **Close the socket on `pagehide`.** MEASURED: Chrome leaves a navigated-away page's WebSocket open server-side; without the client closing it, the other tab saw a ghost until the heartbeat reaped it (≤60s) and re-entries inflated the count.
- **Never per-frame React state for network.** Roster changes re-render; movement mutates refs.
- **`move` carries velocity** so receivers extrapolate; a stop is v=0. Drift correction every 250ms only if >0.75u off.
- **Write policy** (`game/persistence.ts`, keyed by IDENTITY — two tabs share one record): saved when the identity's LAST session disconnects IF dirty, else ≤ once/30s if dirty, never on a tick. The client writes through `data:patch` (shallow merge, `PLAYER_DATA_MAX_BYTES` cap, validated in `validatePatch` — where typed keys get checked once the JSON shape exists); the server echoes the merged blob to every session of that identity. `PlayerData`'s shape is still the open placeholder in protocol.ts. Boot REFUSES a stale schema (`DB_AUTO_MIGRATE=1` only for an empty volume's first boot). Order for schema changes: `db:migrate` on the live db (railway ssh), then `deploy`.
- **Windows can't deliver SIGTERM** to a child process — the shutdown flush is unit-tested (`server/test/persistence.test.ts`, on a throwaway SQLite), not by signal.
- The old gh-pages deploy, `homepage`, and `predeploy` are gone; `CNAME` at the repo root is a leftover to delete once DNS points at Railway.

## Entity sync (Phase 6, Sept 2026) — the SERVER runs every actor's state machine

> **Read [`NPC_TRACKING.md`](../NPC_TRACKING.md) first** — the plain-language write-up of how NPCs sync across clients and how to program a new NPC's movement/states (the beeble as the template). This section is the dense reference.

Built on the Phase 2 transport, no new runtime dependencies (esbuild joins the server's DEV deps: the server is BUNDLED because it imports the client's Three-free files from `src/`). Server: `server/src/game/entities/manager.ts` (the simulation + relay) reads the ACTOR CATALOG (`ACTOR_CATALOG` in `src/world/domains/configs.ts`, derived by `actorCatalogOf` from every domain's biome specs: id → stateMachine + body/collider/movement, or a building's hull attrs). Shared: `src/objects/actors/spec.ts` (ActorSpec), `state/runner.ts` (Three-free machine core), `state/motion.ts` + `state/animation.ts` (the two output channels), `state/types.ts`. Client: `src/net/entities/` (entityStore, interpolation, posePlayback, useSyncedEntity), the actor base (`Actor.tsx`), `ModelActor.tsx` (owns the behavior wiring) + `kinematicMover.tsx` + `animationPlayer.ts`, `state/useStateMachine.ts`, `state/useMouseEvents.ts`. Tests: `server/test/{entities,catalog,persistence,physics}.test.ts` (`npm test` in server/ — runs the real beeble machine and a free-moving test kind on the server), `src/objects/actors/state/{motion,animation}.test.ts`.

**Authority: the server, always. No client owns anything, so no player is favored (PvP-fair).** Each registered actor's state machine — THE SAME CONFIG FILE the client has (`beeble/stateMachine.ts`), written once — runs on the server at 10Hz with the NEAREST player in the domain as "the player"; the machine's `ctx.motion` output drives its body on the server physics world and the server publishes changed fields (a stamped pose snapshot, the whole animation-channel state `anim`, state id `sm`, replicated `state`) to the registrants. Every client is placed to match by SNAPSHOT INTERPOLATION (`src/net/entities/interpolation.ts`, pure + unit-tested): every positional update carries the tick's SERVER time `st`; the client keeps the last snapshots per entity and draws it as it was INTERP_DELAY_MS (200ms = 2 ticks) ago on the SERVER clock, interpolating between the two bracketing snapshots — message ARRIVAL time plays no part, so main-thread hitches and bunched packets cannot overshoot, slide or lurch, and a stop lands exactly where/when the server stopped. Rules: past the newest snapshot extrapolate ≤ 250ms then HOLD; a segment much longer than the publish interval is an IDLE GAP = hold at the old pose until one interval before the new one (MEASURED: lerping across the gap hopped ~0.5u the frame the first moving snapshot arrived); consecutive snapshots > 40u apart = a relocation (restart/respawn), no lerp; a per-actor render clock SLEWS (±10%) toward server-time−delay so a re-estimated clock offset never steps the picture. Animation is applied on the SAME delayed clock: the published `anim` state carries its own server-time clocks (`t0`, `pausedAt`, `changedAt`), `animationPlayer.ts` applies it once the render clock reaches `changedAt` and computes the exact clip time from them — so the idle clip starts exactly as the interpolated body reaches the stop, and pause/resume/speed changes land in phase too. This REPLACED (a) the chase/feedforward/0.5u deadzone/6u snap/local-y mover layer and then (b) arrival-time extrapolation eased toward — both produced catch-up hops and slides under real browser load that a headless probe could never reproduce (headless = no hitches). The kinematic mover only PARKS the capsule at the sampled pose so the local player collides with the NPC. `body: "kinematic"` keeps its local gravity/KCC integration ONLY for `serverSynced={false}` actors. NOTE when verifying ANY of this: dotcomma.io runs the last DEPLOYED release — an uncommitted working tree is only ever visible at localhost:3000 (`npm run dev`); a teleport report from production was once misattributed to local changes. ModelActor's runner MIRRORS the server's state id (with the server's motion output injected) so state-keyed visuals (head tracking, sphere-inflate) run where there is a scene. Every mouse INPUT (hover, clicks, scroll — `runner.ts` `mouseActionOf`) is forwarded (`useMouseEvents`, owned by ModelActor) and raised on the server machine's blackboard, gated by the machine's own distance trigger; inputs cross the wire, never triggers. `serverSynced={false}` opts an instance out (purely local, same code path). `serverSynced` is a `GameObjectAttributes` field: actors default true; dressing/foliage default false and have NO implementation (stateless deterministic scenery — nothing to publish; `true` logs a one-time warning).

**THE authoring contract (runner.ts header):** a StateMachineConfig expresses movement/facing through `ctx.motion` (`move(vx,vz)`, `heading(angle,speed)`, `toward(x,z,speed)`, `fly(vy|null)` — null = gravity/ground; for `movement:"free"` null = 0 —, `stop()`, `face(yaw)`, `faceHeading()`, `faceToward`, `turnToward(x,z,maxStep)`, reads `yaw`/`angleTo`) and animation through the state's `animation: { clip, loop?: "repeat"|"once", speed? }` shorthand or `ctx.animation` (`play/pause/resume/stop/setSpeed`), and never the scene for those; anything scene-bound (bones, geometry) must guard on `ctx.groupRef.current` (null on the server); a PER-PLAYER effect (sound, dialog) is `if (ctx.groupRef.current && ctx.input.leftClick)` in the state the click lands in — mirror flags are this player's only — while the state it transitions INTO runs on every client; no Three at RUNTIME in a config (`import type`). The server's simulation time is TICK-based (`elapsed += dt`), so `stateElapsed` agrees with `delta` exactly as on the client. Adding a synced NPC = `stateMachine.ts` (transitions hold trigger OBJECTS — the runner collects them and throws on an unknown trigger id/target outside production) + `spec.ts` (id, stateMachine, `body: "kinematic"`, `collider`, `movement: "ground" | "free"`, model + spawn attrs) + a `{ actor: SPEC }` entry in a biome spec's `actors` (which is what catalogs it) — no component, no actor.tsx, no server file. The server's input reach check is `serverInteractReachSq(spec)` = (`interactReach` ?? 5, the client raycast's reach) + 3u slack. `movement: "free"` is a `FreeBody` on the server (velocity integrated, no gravity/ground/holds) and the mover's free branch on the client. `dynamic` (pushables) is NOT implemented.

- Entities exist because clients register them (position-based ids); first registration creates the record and starts the machine; zero registrants = disposed. Interest = registrants, per domain; a registration is answered with the full record (late joiners covered).
- The server owns x, y AND z (its physics world stands on the same terrain as the client — see Server physics). Random is fine (single authority). Machine state on the server is lost when the last viewer leaves (fresh machine next time).
- Replicated `state` is server-owned and toggled via interact actions (`door:<i>` is generic — a kind with a building `hull` gates it on the door's own plan position and index, any other kind on its origin); doors' state lives only while someone is near (nothing persists it).
- **Server physics (Sept 2026)** — `server/src/game/physics/`, headless `@dimforge/rapier3d-compat` (THE CLIENT'S copy: the server declares no Rapier dependency, esbuild bundles the root install's package — one package/version/WASM/class-identity set by construction, asserted in `server/test/physics.test.ts`; boots with `await init()`, no Node flags). MODULES, each one thing: `physicsWorld.ts` PhysicsWorld — the Rapier world (initialized with the PHYSICS_DOMAIN's SHARED config from `src/world/domains/configs.ts`), `step()` timing, `ensureQueries()`, capsules, and two `ChunkStore`s on one `JobQueue`; `chunks.ts` JobQueue (budgeted `workFor(ms)`, each job's `step(deadline)` returns done) + ChunkStore<T, D> (REFCOUNTED keyed resources built by queued jobs: `request/release/isReady`, an optional `fetch` for off-thread data; nothing is built for the whole world; a chunk released while pending and requested again is rebuilt — it used to be lost to the queue's key dedupe); `chunkGenerator.ts` + `chunkGenerator.worker.ts` sample the heightfields and dressing points OFF the tick thread (the same `computeVertexData`, bit-identical — a test compares it to the in-place path, which stays as the fallback and for tests/tools), so the tick thread only creates Rapier bodies (MEASURED, 2 players walking the city: tick p95 13.4–15.9 → 8.5–10.7 ms, max 99–124 → 19–30 ms; +~60 MB RSS for the worker's caches) + `chunkIndicesNear`; `terrain.ts` the LOD1 heightfield sampled EXACTLY like terrain.worker.ts (fround'd local grid, z-flip, column-major, body at the chunk center — bit-identical ground to the player's), row by row for incremental builds; `obstaclePoints.ts` (Rapier-free enumeration) + `obstacles.ts` (the bodies) every spec in `objects/dressing/catalog.ts` (street lamps / traffic signals / utility poles / bridge decks) as the client's exact colliders (cuboids; a bridge chord's triangle mesh) per 256u dressing chunk: each spec's enumerator from `objects/dressing/enumerators.ts` run with the spec's placement, each point through its `bodiesOf` (`ObstaclePoint.pitch` composes the deck chords' tilt as `qY·qZ`); `buildings.ts` a building's SEALED convex hull — the client's `buildProxyHullVertices` over the client's `generateBuildingPlan`, seeded `${round(x)}_${round(z)}` like Building.tsx, shaped by the kind's hull attributes (`building/spec.ts`), cached per seed; `walker.ts` a kinematic capsule driven by THE shared resolver `src/physics/characterMovement.ts` (`step(dt, vx, vz, vy)`, `placeFeet`); `npcBody.ts` the NpcBody INTERFACE (`step(dt, vx, vz, vy)` before the world step with the machine's motion output, `resolvePose()` after it returns feet-y position + ACTUAL quantized velocity) + `createNpcBody(pw, spec, x, z)` choosing by the spec's `movement`: `groundBody.ts` GroundBody = Walker + the chunks it HOLDS (its own + the neighbor within 12u of an edge, terrain AND dressing, re-evaluated after 4u of travel; a body whose holds aren't built yet simply waits) + the player's stuck escape and 2u analytic backstop; `freeBody.ts` FreeBody = velocity integrated as-is (flyers/swimmers — no gravity, no ground, no holds, no Rapier body); `playerBodies.ts` PlayerBodies — a capsule per player (`src/player/spec.ts` dimensions) in a domain with NPCs, following the reported center position, reconciled per tick. The DomainConfig is no longer hand-assembled on the server: `src/world/domains/overworld/config.ts` builds it from the region/biome SPEC files the JSX itself mounts (the flatten pads from the biomes' `actors`), and the `<Domain>` commit console.errors in dev when its own config differs. `entities/manager.ts` is the registry + tick orchestration: work → players.sync → ensureQueries → machines + `npc.step` → ONE `world.step()` → `npc.resolvePose` → `publish.ts` (`publishTick` diffs pose/yaw/clip/state against what registrants last saw; any positional change goes out as a complete server-time-stamped SNAPSHOT `{st,x,y,z,vx,vy,vz,ry}`); hulls queue on the same JobQueue (a city entry registers hundreds of buildings). Kinds come from the catalog: `beeble` = `BEEBLE_SPEC` (machine + capsule, ground); `building`/`skyscraper`/`house` = hull specs. Every 10s `[physics] …` logs npcs/players, tick max, step/work ms, slowest job step, collider/body/chunk counts; a tick > 50ms warns. Tooling: `npm run physics:demo` (`cli/physicsDemo.ts` + `cli/terrainScan.ts`) drops a capsule, climbs a 17° slope, slides off a 44° one. MEASURED gotchas: (1) Rapier's slope wall alone does NOT stop a 44° climb on heightfields — `computedGrounded()` holds true on steep faces, gravity resets, the capsule creeps up ~2.6u/s; the resolver's ray-gated support (hit within snap reach AND ≤ 40°) is what makes it slide; (2) colliders created since the last `step()` are invisible to queries until `updateSceneQueries()` — a beeble fell 1u through a just-built heightfield and sat wedged (`ensureQueries()` runs after generation every tick); (3) BUILD: the bundle externalizes only express/ws (+ three/react so a leak fails at boot) and BUNDLES rapier/delaunator/noise-ts/seedrandom from the root install — as externals Node's CJS interop made `import Noise from "noise-ts"` the exports object and the built server died at boot (tsx dev hid it).
- History: server-behaviors-file (rejected: behavior written twice) → client ownership (rejected: first registrant hosted → unfair) → THIS. `@types/three` (0.170) is newer than runtime three (0.157): the compiler can't catch r159+ API use (TrafficLights branches on `updateRange` vs `updateRanges`). The source is kept working on BOTH 0.157 and 0.170 (verified Oct 2026: a production build, the client suite and screenshots against 0.170 in a scratch copy); upgrading is `npm install three@0.170.0 --save-exact` and nothing else — drei is imported per module (`@react-three/drei/core/…`) because drei 9.87's index imports `LinearEncoding`, which r162+ no longer exports (CRA fails the build on it). Day/night runs off the shared server clock.
