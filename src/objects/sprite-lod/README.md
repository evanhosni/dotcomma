# Sprite LOD

## How it works

A far tier for actors. A kind with `spriteLod: { renderDistance }` on its spec is replaced, past its own `renderDistance`, by an upright camera-facing billboard (a "sprite") that stands in out to the sprite tier's `renderDistance`. Every tier is just a render distance under ONE radius rule ([../actors/spawning/radii.ts](../actors/spawning/radii.ts)): it loads at `renderDistance + footprint/2` and drops at 1.2× that. Buildings are the first member (handoff at 625u, sprites to 3000u).

- **Handoff** ([detail.ts](detail.ts)): the actor base (`useActorLifecycle({ spriteHandoffDistance })`, set by the pool) spawn-fades out past the handoff distance (±`SPRITE_LOD_HYSTERESIS` 20u) and is held hidden, group not drawn; back inside it fades in from where it was. It appears already hidden when its group first shows up beyond the handoff. Every frame its fade value changes it reports it by spawn-point id (`setSpriteDetail`, 0 on unmount); the sprite draws exactly the screen-door pixels the actor discards, so every pixel is drawn once. No report = a fully shown sprite (unbuilt, unmounted or never spawned). The writer never imports the reader.
- **Loading** ([spriteWorker.ts](spriteWorker.ts)): every 250u spawn chunk whose area comes within the reach (the largest sprite spawn radius) of the camera, nearest first (the reach rule is `chunkGap` in [utils.ts](utils.ts), shared with the threads), on up to two `spawn.worker` threads of the tier's own (`GENERATE_SPRITES`). An idle thread gets the next ≤12 chunks at once, under a 120ms budget; what it did not finish goes out again. A chunk whose generation throws is retried once, then loaded empty until evicted. A request unanswered for 20s restarts its thread; an epoch keeps stale answers out. Chunks entirely past the drop distance are evicted about every 30 frames, and each thread forgets its cached placement by the same rule.
- **Placement** ([describers.ts](describers.ts)): the pool's own placement (`generateForChunk`, all kinds, the pool's max footprint), then each sprite kind's describer per point (`SPRITE_DESCRIBERS`). A sprite's id is its actor's (`spawnPointId`). Describers are Three-free and pure.
- **Drawing** ([SpriteLods.tsx](SpriteLods.tsx): rebasing and the loaded set; [LookMesh.ts](LookMesh.ts): one look's mesh and instance buffer; [spriteMaterial.ts](spriteMaterial.ts)): one instanced draw per look, never frustum-culled, rebased on the chunk grid near the camera (float64 on the CPU; the origin moves only when the camera strays 1000u, which repacks everything). In between, a chunk arriving appends its sprites and a chunk leaving swap-removes its own, and only the touched ranges upload (building/DECISIONS.md 17). Instance layout ([layout.ts](layout.ts)): offset, size, the LOD vec4 (detail, renderDistance, born, spare) and 20 data floats for the look. Growing a buffer builds a new geometry (`ensureCapacity`): three fixes the draw cap on a geometry's first draw. The material is scene-lit (roughness 0.85, metalness 0.05 by default), curved, and dithers by detail × arrival (0.6s) × far fade (the last 12% of the tier's distance). A sprite fully covered or fully faded collapses and costs nothing.
- **Debug**: `__spriteLod()` in the console: `ready`, `idleWorker`, `reach`, `chunks`, `pending`, `missing`, `nearestMissing` (to the chunk's nearest edge), `sprites` (per look: `look`/`instances`/`drawCap`/`visible`/`inScene`), `camera`, `origin`. `instances` above `drawCap` means late chunks are not drawn.

## How to use/add

1. Set `spriteLod: { renderDistance }` on the kind's spec (`building/spec.ts` → `BUILDING_SPRITE_LOD`).
2. Write a Three-free describer `(attributes, x, z) => { width, height, data } | null` that reproduces what the member builds at that point, and add it to `SPRITE_DESCRIBERS`.
3. Write a `SpriteLook` (`types.ts`: fragment, optional emissive/header/uniforms/update) and set it as `spriteLook` on the member component.
4. The member honors the handoff by passing `spriteHandoffDistance` to `useActorLifecycle`. `ModelActor` does not yet, so a GLTF kind with a `spriteLod` is a content error (as is a `spriteLod` with `fadeOut`).
