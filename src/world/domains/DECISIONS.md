# Domains, navigation and addresses — decisions

> Moved verbatim from CLAUDE.md (Oct 2026) to keep it under the context limit. Section names quoted in the text ("Blending", "Rivers", …) refer to the other decision docs listed in CLAUDE.md under "Where the docs are".

## One page, client-side domain switching

**Domains share ONE page** (no router — URL paths are FAKE, `pushState` only; `src/world/domains/navigation.ts`): `src/index.tsx` renders one `<CustomCanvas>` for the active domain — `OverworldDomain` (`src/world/domains/overworld/domain.tsx`) is THE game, one infinite map; EVERY path except `/` is an ADDRESS inside it (see "Addresses" below — `/glitch-city` no longer exists); `HomeDomain` (`src/world/domains/home/domain.tsx`, path `/`) is the landing page and the only other domain (its pieces — the flat grid ground, the CRT address selector, the click-to-enter gate — are in its README). Invariants there: it passes `terrain={false}` (the streaming terrain is overkill for a flat world) and its `HomeGround` sets `terrainLoaded`/`progress` itself (the Player is gated on them); the flat-noise config still COMMITS (zeroed base/road noise, the config-only `home` region and `wire` biome) so the analytic height pipeline — Player backstop/respawn — reads height 0, so don't remove `<Terrain>` or the home region; the CRT's glow light is PARKED at intensity 0 from mount (a light appearing later recompiles every lit shader — the nightfall-hitch class); and `ClickToEnter`'s backdrop must `stopPropagation` (drei's PointerLockControls listens on the DOCUMENT) and then dispatch a synthetic document click so drei locks the element its controls are connected to (`events.connected` — locking an element we pick ourselves engages the browser lock while mouse-look stays dead). **Navigation is CLIENT-SIDE** (`src/world/domains/navigation.ts`): `navigateToAddress(path)` from a gesture is a TELEPORT when already in the overworld (pushes the path, fires `ADDRESS_TRAVEL_EVENT`, which `overworld/FastTravel.tsx` turns into a new `playerSpawn` + a closed terrain gate — `terrainLoaded` false, TerrainRenderer restarts its loading count on a spawn change — so the Player's hold-at-spawn branch carries the capsule there until the ground exists) and a DOMAIN SWITCH into the overworld from home (`switchDomain`, the address kept as the pending destination FastTravel consumes on mount). A switch pushes a fake URL path and index.tsx swaps the domain (`DOMAIN_COMPONENTS`, `world/domains/components.ts`) INSIDE ONE PERSISTENT `<CustomCanvas>` in TWO PHASES — render no domain (old domain unmounts fully: TerrainRenderer's cleanup removes its heightfield bodies from the physics world, which now outlives domains), `resetDomainSystems()` (`src/world/domains/reset.ts` terminates the terrain/spawn/grass/dressing workers + clears their client caches + module chunk state + unpublishes the active domain so `whenDomainReady()` blocks until the next commit), then mount the new domain. The canvas, GL context, compiled shader programs, `<Physics>` world, Player, GameContext and overlays are NEVER torn down, so a switch neither loses the GL context nor recompiles shaders, and pointer lock simply stays held (the locked element persists). Per-domain scene state is therefore a `<Domain>` prop, not a canvas prop: `background` (scene.background) and `playerSpawn` (published through GameContext to the persistent Player); the outgoing `<Domain>` resets `terrainLoaded`/`progress` on UNMOUNT only (child effects run before the parent's, so a mount-time reset would clobber HomeGround's/TerrainRenderer's) and the Player's hold-at-spawn branch carries it to the new spawn. (The previous design remounted a canvas per domain: it force-lost the GL context — logged as `THREE.WebGLRenderer: Context Lost.` — recompiled every program, and needed a `relockPointerAfterSwitch` re-request hack because the locked element was destroyed; all REMOVED.) Real navigation was DELIBERATELY removed: pushState-only history means every entry behind the player is same-document, so the browser BACK button/gesture can only ever fire `popstate` — `navigation.ts` restores the URL and fires `ESCAPE_POD_EVENT` (back = in-game escape pod, it can never unload the game; a sentinel entry is also pushed on first pointer lock because Chrome's history intervention skips gesture-less entries). Refresh really reloads and boots whatever fake path is in the URL. (A refresh-key → rescue-respawn intercept existed briefly and was removed by preference; F5/Ctrl+R ARE cancelable on keydown if ever wanted again — unlike Ctrl+W, which is browser-reserved and uninterceptable outside fullscreen keyboard lock.)

## Config components and the commit

Each domain's config components (`Domain`, `Regions`/`Region`, `Biome`, `Terrain`, `Material`, `Skybox` — in `src/world/components/`, except `Skybox`, which lives with the sky system in `src/world/sky/Skybox.tsx` and is re-exported from `components/`) register into a store during layout effects; `<Domain>` then **commits** the assembled `Region[]` data (each with its `baseNoise`, base `getMaterial`, `riverProbability` and `biomes`) + serializable `DomainConfig` to module-level active-domain accessors (`src/world/domains/utils.ts`) and mounts the global systems (`TerrainRenderer`, `ActorPool`, `SkyboxSystem`). Non-React code (workers init, Player) reads from those accessors — `getActiveRegions()`, `getActiveDomainConfig()`, `getTerrainParams()`, or `await whenDomainReady()`. The types live in `src/world/types.ts` (`TerrainParams`, `CityConfig`, `RiverConfig`, `RegionSpecBase`/`Region`, `BiomeSpec`/`Biome` (+ `water`), `BlendWidthProps`) and `src/world/domains/types.ts` (`ActiveDomain`; `DomainId` re-exported from `src/net/protocol.ts`, where `DOMAIN_IDS` defines it once); defaults in `src/world/defaults.ts` (`DEFAULT_TERRAIN_PARAMS` incl. `river`, `DEFAULT_RIVER_TEXTURE`). `<Region spec>` and `<Biome spec>` take the folder's `spec.ts` object and register ALL of it (noise/baseNoise and the biome's `actors` included); `<Regions specs components>` / `<Region biomes>` render the component maps (keyed by spec `name`) IN SPEC ORDER — a `null` entry renders the bare `<Region spec>`/`<Biome spec>`, so a config-only spec needs no `.tsx` (the home domain) — and each `<Region>`/`<Biome>` asserts it is the spec its parent's list put there (dev throw), so JSX order cannot drift from the voronoi order. `world/domains/configs.ts` lists every domain's region specs (`DOMAIN_REGIONS`); the server's ACTOR CATALOG is derived from them (`ACTOR_CATALOG`: every placed kind with something to simulate). `overworld/config.ts` builds the SAME config from the same spec list (`OVERWORLD_REGIONS`, `overworld/regions/index.ts`) for the server (`buildDomainConfigFromSpecs`, flatten pads derived from the biomes' `actors`); `assembleDomainConfig` asserts unique region/biome ids and names (lowercase letters — address words and shader function names); the commit console.errors in dev when the two differ.

## Scope-aware Material/Skybox

`Material`/`Skybox` are **scope-aware**: their meaning depends on whether they're mounted under `Domain`, `Region`, or `Biome` (see the tree above). `Terrain` is domain-only (dev throw under a region/biome: relief is the spec's `baseNoise`/`noise`). `Material` takes `shader` + `textures` (uniform name → file, `_material.fromShader`) or a `getMaterial`; under a region is its BASE material (`getMaterial` → `<region>_base_frag`, the surface a biome's own texture fades into over its blend width — "presence" under Blending); under the domain it is the river-bed texture. Skyboxes: a biome-scoped sky wins over a region-scoped one; below those the REGION skies are MIXED by the place's region weights (`getPlaceInfo`, region-level blend widths), so the sky cross-fades with position across a region edge; the place is polled off-thread through the dressing worker (`PLACE_INFO`) only when scoped skyboxes exist. (The separate `utils/voronoi/` worker that used to answer this was a second, warp-less copy of the pipeline and was DELETED.)

## Addresses

**Addresses — the URL is a place** (`src/world/domains/overworld/address.ts`, Three-free; `FastTravel.tsx` is the React glue). A path is `/<region words>/<biome words>` — `famous-sprawl/velvet-town` (a city cell in a city region), `amber-lakelands/twin-pool` (a lake), `deep-winterland/hushed-spire` (a mountain). BOTH the region-grid cell and the biome-grid cell get a name that is a BIJECTIVE ENCODING of its cell coordinates (zigzag → bit-interleave → the low 12 bits scrambled by a fixed odd multiplier → 8-bit ADJECTIVE words, then one 4-bit NOUN drawn from the THEMED list of what stands there: `REGION_NOUNS`/`BIOME_NOUNS` have a 16-word list per region type and per biome type), never a hash and never a registry: nothing is enumerated, a name nobody has visited decodes exactly. Names are TWO words within ±32 cells of the origin, three within ±512, four beyond; the noun decodes from ANY theme's list (`REGION_NOUNS`/`BIOME_NOUNS` keyed by name, `GENERIC_NOUNS` for the rest; every noun unique across all lists, asserted at load), so the theme only changes the word, never the place. Type forms: `/city` = the city region's cell nearest the world ORIGIN (ring scan of cell rolls — the same place for everyone), `/snow/mountain` = the mountain cell nearest that region cell's site; the CRT pages use them. Travel lands on the biome cell's voronoi SITE (warp-inverted to world space), lifted onto the water where the site is in a lake. The address bar follows the player (`replaceState`, keeping the back trap's entry; `pathForPlace`): the words name the cells under the player, the nouns the region/biome found there (`getPlaceInfo`). **FROZEN**: the word lists (256 adjectives + 16 nouns per theme, unique across every list, append-only, never reorder), the scramble constant, the seed, the region/biome order and the grid sizes all decide which words mean which place; `address.test.ts` pins fixed vectors (`amber-lagoon` = cell 0,0 with the lake noun) — a failing vector means every link ever written has moved. Debug: `window.__dotcomma.travelTo(x, z)`.

## Key patterns (moved from CLAUDE.md)

- **Declarative hierarchy, data-model core** — content is declared as JSX (each domain's `domain.tsx`), but the commit produces a plain `Region[]`/`Biome[]` data model (`src/world/types.ts`). Non-React code reads it from the active-domain accessors (`src/world/domains/utils.ts`: `getActiveRegions()`, `getActiveDomainConfig()`, `await whenDomainReady()`).
- **Hierarchy ownership rule** — code lives at the level it belongs to: biome-specific things in the biome folder, region-specific in the region folder, domain-specific in the domain folder; only genuinely shared systems live above the domains (world/, objects/, utils/, lighting/, vfx/).
- **Pattern files** — folders keep their data/config in consistently named files: `types.ts`, `constants.ts`, `defaults.ts`, `utils.ts` at the appropriate level (e.g. `world/types.ts`, `world/defaults.ts`, `world/domains/constants.ts`). No grab-bag singleton modules.
- **Specs are data, JSX renders them** — everything the server's config needs (ids, names, noise, flags, blend widths, biome order, a biome's `actors`) lives in `spec.ts`; `<Regions>`/`<Region biomes>` render component maps IN SPEC ORDER, so JSX and config cannot drift.
- **Scope-aware config components** — `<Material>`, `<Skybox>` mean different things under `<Domain>`, `<Region>`, or `<Biome>` (they read `RegionContext`/`BiomeContext`); `<Terrain>` is domain-only. Registration components render `null`; visual components (e.g. `GrassField`) render normally.
