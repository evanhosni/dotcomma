# dotcomma

An exploration-based procedurally-generated 3D game built on React Three Fiber. Players explore infinite terrain across diverse biomes and encounter spawned NPCs/objects. The codebase is designed to be modular — new domains, regions, biomes, game objects, and systems should be easy to add without touching core infrastructure.

> **Maintenance note:** This file is NOT auto-updated. When you add new systems, rename directories, change conventions, or make architectural changes, ask Claude to update CLAUDE.md to reflect them.

## Tech Stack

- **React 18** + **TypeScript** (strict mode)
- **Three.js** via `@react-three/fiber`, `@react-three/drei`, `@react-three/rapier` (physics)
- **No router** — one page, one canvas; domain switching is client-side with fake `pushState` URL paths (`src/world/domains/navigation.ts`)
- **Craco** (CRA + webpack customization, `.glsl` files loaded as raw assets)
- **Web Workers** for heavy computation (Voronoi/Delaunay, terrain data)
- **Noise**: `noise-ts` (Simplex/Perlin), `seedrandom` (deterministic RNG)
- **Delaunator** for Voronoi diagrams

## Commands

- `npm run dev` — server + client together (`scripts/dev.mjs`: tsx watch on :8080 + craco on :3000, prefixed output, Ctrl+C stops both; first run creates + migrates the local SQLite)
- `npm start` — client dev server only (craco); `npm run dev:server` — game server only
- `npm run build` — production build
- `npm test` — jest tests (package.json sets `transformIgnorePatterns` so ESM deps — delaunator, robust-predicates, noise-ts — transform; run headless with `$env:CI="true"; npm test -- --watchAll=false`)
- `npx tsc --noEmit` — type check

## Architecture

### Content hierarchy — DOMAIN → REGION → BIOME, everything is a component

```
<Domain>                     // one switchable world (home, overworld); global rulesets + systems
  <Terrain/>                 //   global terrain rules (seed, grid sizes, road noise, river config, city config, default blend widths)
  <Material/>                //   river BED texture (under every river channel)
  <Skybox/>                  //   default sky
  <PostProcessing/>          //   global post-processing
  <Regions specs components> // renders the domain's region spec list IN ORDER (= voronoi order; config.ts reads the same list)
  <Region spec biomes>       // spec = id/name/baseNoise/blend widths/riverProbability/biome order; `biomes` = components by name
    <Material/>              //   its BASE material — what a biome's own texture fades into at the biome's edge (presence)
    <Skybox/>                //   its sky (mixed by position across region edges)
    <Biome spec>             // rendered by <Region> in spec.biomes order; spec: joinable, noise|water, blend widths, `actors`
      <Material/>            //   biome fragment shader (<Material shader textures>)
                             //   ACTOR class: per-object spawns (identity/state/interaction) are
                             //     DATA — spec.actors: [{ actor: ActorSpec, …overrides }], registered by <Biome>
      <Dressing>             //   DRESSING class: mass stateless scenery, instanced per chunk;
        <StreetLamps/>       //     group props (renderDistance) are shared defaults; children
        <RoadMarkers/>       //     take their placement knobs as props
      </Dressing>
      <Foliage>              //   FOLIAGE class: mass GPU vegetation (per-instance attributes,
        <GrassField/>        //     shader animation); same group-defaults pattern
      </Foliage>
      <Skybox/>              //   optional per-biome sky override
    </Biome>
  </Region>
</Domain>
```

**The hierarchy is also the FOLDER hierarchy** (`src/world/domains/<domain>/regions/<region>/biomes/<biome>/`): everything specific to a biome lives in that biome's folder, everything specific to a region in its region folder (`region.tsx`, `spec.ts`, `shaders/base.glsl` = the region's BASE material), domain in its domain folder (e.g. `CityLights` lives in the city biome's folder because only the city mounts it). Only genuinely shared/global code lives above the domains. A REGION is a group of biomes with its own base noise, base material, sky and `riverProbability`, partitioned by a voronoi grid above the biome grid (`regionGridSize` 3000 → biome `gridSize` 500). Nothing is larger than a region, and no edge — region or biome — is a hard boundary: terrain height, material and sky all cross-fade into the neighbor (see "Blending"); rivers are the edges of their own grid and cross everything (see "Rivers"). The overworld has four: **city** (city + grass biomes on the default base, grass base material, `riverProbability` 0.35), **desert** (dust + salt-flat biomes on their own simplex base, sand base, 0.15), **snow** (tundra + mountain on a slow perlin base, snow base, 0.55), **ocean** (lake biomes — bowls under a blended water level — on a near-flat base, wet-sand base, 0.6). (The DIMENSION level and the flat `test` dimension of the previous round were REMOVED in Sept 2026: a third nested grid bought nothing a region with its own base noise and sky does not.)

**The three game-object classes** (`src/objects/` — the ATTRIBUTE HIERARCHY is one file, `src/objects/types.ts`: `GameObjectAttributes` (every class — renderDistance, colliderDistance, quantization, placement filters `biomeIds`/`heightRange`/`slopeRange`/`roadDistanceRange`, density/footprint) → `ActorAttributes` / `DressingAttributes` / `FoliageAttributes` (what only that class has) → member attributes next to the member (`ModelActorAttributes` in `actors/ModelActor.tsx`: model, scale, collider options; `BuildingAttributes` in `actors/building/types.ts`: shell/window/interior knobs). A field lives at the highest level where at least two users share it): **ACTORS** are objects with their own identity, state, or interaction — creatures, buildings — each mounted as its own React component through the spawn lifecycle (`ActorPool`); a kind is ONE Three-free `ActorSpec` (`<actor>/spec.ts`: model/placement/simulation knobs + the member `component` name), `describeActor(spec)` is its descriptor (`ActorDescriptor<ItsAttributes>`), and every attribute on it is forwarded to each instance as props (`ActorProps<A>` — minus the spawn-only ones in `SPAWN_ONLY_KEYS`, one list driving both the `Omit` type and the pool's runtime strip), so a member's knobs are set on the spec and overridden per biome mount (`BiomeSpec.actors`) — no wrapper components (the Apartment/BigBeeble/XL/XXL wrappers and the `Skyscraper` component were deleted for exactly this). **DRESSING** is mass stateless identical scenery — street lamps, road markers, traffic lights, power lines — rendered as InstancedMeshes per 256u chunk with zero per-object components. **FOLIAGE** is vegetation at another order of magnitude — up to ~32k instances per 64u chunk, placement streamed as Float32Arrays straight into GPU instance attributes, animation (billboarding/sway) in the vertex shader. All three get off-thread deterministic placement (spawn.worker / dressing.worker / foliage.worker).

**EVERY game object is built on its class's BASE, and each base owns ALL logic its members share** — this is structural, not stylistic: a world-wide effect (world curvature, vertex quantization, lamp glow, the spawn fade-in, the shared frame driver, GPU warm-up) is implemented ONCE per base and inherited by belonging to the class. An object that hand-rolls what its base does will silently miss the next one (this is exactly what happened before the bases were consolidated: adding curvature needed six separate patch sites).

| class | base | what the base owns | a member is |
|---|---|---|---|
| ACTOR | `objects/actors/Actor.tsx` | `useActorLifecycle` (ONE shared frame driver, the single 2D squared distance, spawn fade-in (+ fade-out for `fadeOut` actors) + hard-kill despawn, frustum visibility + warm-up, distance-gated colliders with hysteresis and a global activation throttle, a "near" gate for dynamic content, matrix freezing) and `prepareActorMaterial` (quantization + lamp glow + curvature + spawn fade) | `<ModelActor>` (`actors/ModelActor.tsx`, the standard GLTF actor: pooled clone, its colliders, animation LOD) — or, for actors that own their geometry and render shape, `useActorLifecycle` directly (`Building`) |
| DRESSING | `objects/dressing/Dressing.tsx` | `useDressingChunks` (camera-following 256u chunk lifecycle on one budgeted queue), `useDressingAssets` + `prepareDressingMaterial` (creation, curvature, spawn fade, disposal; each chunk fades in as it is added), `instancedFromPoints` / `finalizeInstancedChunk` (assembly + far-from-origin rebase + culling bounds + warm-up), `useChunkRegistry` | a component with ONLY its own placement query, geometry/materials, and optional animation (`StreetLamps`/`FreewayLamps`, `RoadMarkers`, `TrafficLights`, `PowerLines`) |
| FOLIAGE | `objects/foliage/Foliage.tsx` | the ENTIRE pipeline — chunk lifecycle, worker streaming, the instanced billboard mesh, the shader (billboarding, sway, per-instance distance fade, quantization, curvature, spawn fade per chunk, night dim), the distance LOD, disposal | `createFoliage({…})` with a plant's art + defaults; every knob stays overridable at the mount (`grass/GrassField.tsx` is ~60 lines) |

Rule of thumb: unique geometry, interaction, or behavior → actor; many + identical + stateless → dressing; thousands-per-chunk vegetation → foliage. Both `<Dressing>`/`<Foliage>` group components come from one defaults-group factory (`src/objects/utils.tsx`).

**Domains share ONE page** (no router — URL paths are FAKE, `pushState` only; `src/world/domains/navigation.ts`): `src/index.tsx` renders one `<CustomCanvas>` for the active domain — `OverworldDomain` (`src/world/domains/overworld/domain.tsx`) is THE game, one infinite map; EVERY path except `/` is an ADDRESS inside it (see "Addresses" below — `/glitch-city` no longer exists); `HomeDomain` (`src/world/domains/home/domain.tsx`, path `/`) is the landing page and the only other domain: it passes `terrain={false}` to `<Domain>` — the streaming chunk terrain system is SKIPPED (overkill for a perfectly flat world) and the ground is `HomeGround` (`domains/home/HomeGround.tsx`): ONE static black fill plane + a lit white-wireframe grid plane (MeshStandardMaterial, grid spacing 4.375u = the old LOD1 chunk density) that follows the camera snapped to the grid, + one flat cuboid collider. The region/flat-noise config still COMMITS (zeroed base/road noise, `home` region, height-less `wire` biome) so the analytic height pipeline — Player backstop/respawn via `getVertexData` — keeps reading height 0; don't remove `<Terrain>` or the home region when touching this domain. The scene has ZERO ambient light, so the grid renders pure black until `CrtMonitor` (`domains/home/CrtMonitor.tsx`) — a HUGE 4:3 CRT at [0,2.2,-36], the address selector — powers on ~1s after the player first clicks in (pointer lock; classic line-expand turn-on, eased fade). A switch pushes a fake URL path and index.tsx swaps the domain INSIDE ONE PERSISTENT `<CustomCanvas>` in TWO PHASES — render no domain (old domain unmounts fully: TerrainRenderer's cleanup removes its heightfield bodies from the physics world, which now outlives domains), `resetDomainSystems()` (`src/world/domains/reset.ts` terminates the terrain/spawn/grass/dressing workers + clears their client caches + module chunk state + unpublishes the active domain so `whenDomainReady()` blocks until the next commit), then mount the new domain. Each domain's config components (`Domain`, `Regions`/`Region`, `Biome`, `Terrain`, `Material`, `Skybox` — in `src/world/components/`, except `Skybox`, which lives with the sky system in `src/world/sky/Skybox.tsx` and is re-exported from `components/`) register into a store during layout effects; `<Domain>` then **commits** the assembled `Region[]` data (each with its `baseNoise`, base `getMaterial`, `riverProbability` and `biomes`) + serializable `DomainConfig` to module-level active-domain accessors (`src/world/domains/utils.ts`) and mounts the global systems (`TerrainRenderer`, `ActorPool`, `SkyboxSystem`). Non-React code (workers init, Player) reads from those accessors — `getActiveRegions()`, `getActiveDomainConfig()`, `getTerrainParams()`, or `await whenDomainReady()`. The types live in `src/world/types.ts` (`TerrainParams`, `CityConfig`, `RiverConfig`, `RegionSpecBase`/`Region`, `BiomeSpec`/`Biome` (+ `water`), `BlendWidthProps`) and `src/world/domains/types.ts` (`ActiveDomain`; `DomainId` re-exported from `src/net/protocol.ts`, where `DOMAIN_IDS` defines it once); defaults in `src/world/defaults.ts` (`DEFAULT_TERRAIN_PARAMS` incl. `river`, `DEFAULT_RIVER_TEXTURE`). `<Region spec>` and `<Biome spec>` take the folder's `spec.ts` object and register ALL of it (noise/baseNoise and the biome's `actors` included); `<Regions specs components>` / `<Region biomes>` render the component maps (keyed by spec `name`) IN SPEC ORDER, and each `<Region>`/`<Biome>` asserts it is the spec its parent's list put there (dev throw), so JSX order cannot drift from the voronoi order. `overworld/config.ts` builds the SAME config from the same spec list (`OVERWORLD_REGIONS`, `overworld/regions/index.ts`) for the server (`buildDomainConfigFromSpecs`, flatten pads derived from the biomes' `actors`); `assembleDomainConfig` asserts unique region/biome ids and names (lowercase letters — address words and shader function names); the commit console.errors in dev when the two differ.

`Material`/`Skybox` are **scope-aware**: their meaning depends on whether they're mounted under `Domain`, `Region`, or `Biome` (see the tree above). `Terrain` is domain-only (dev throw under a region/biome: relief is the spec's `baseNoise`/`noise`). `Material` takes `shader` + `textures` (uniform name → file, `_material.fromShader`) or a `getMaterial`; under a region is its BASE material (`getMaterial` → `<region>_base_frag`, the surface a biome's own texture fades into over its blend width — "presence" under Blending); under the domain it is the river-bed texture. Skyboxes: a biome-scoped sky wins over a region-scoped one; below those the REGION skies are MIXED by the place's region weights (`getPlaceInfo`, region-level blend widths), so the sky cross-fades with position across a region edge; the place is polled off-thread through the dressing worker (`PLACE_INFO`) only when scoped skyboxes exist. (The separate `utils/voronoi/` worker that used to answer this was a second, warp-less copy of the pipeline and was DELETED.)

**Blending — no boundary anywhere, ever** (`accumulateWallFields` in `utils/workers/zoneBlend.ts`; its header comment is the math). Two nested voronoi grids assign a ZONE (region × biome) to every point; the walls between zones (Delaunay duals) are the only edges in the world, and every edge CROSS-FADES: heights on the CPU, the material per PIXEL in the shader, the sky by position. The mechanics, and why each is the way it is:
- **One wall pass per vertex.** For each nearby wall a|b at distance d, zone a's indicator is `smoothstep(-h_b, +h_a, s)` with `s` the signed distance into a: each side contributes ITS OWN half-width on its own side, and the two indicators sum to exactly 1 along the wall. The vertex's own zone takes the MIN over its walls, foreign zones the MAX over theirs — both continuous, so no per-triangle steps. A wall between two zones the vertex is in NEITHER of contributes what a vertex on the far side of that wall would compute — a function of the wall alone (using the vertex's OWN half-width there was tried and REJECTED: the field then changed value across a third zone's wall).
- **Indicators combine by CRISPNESS PRECEDENCE, never by plain normalization** (`combineZoneWeights`; tiers of equal `heightHalf`, crispest first: a tier claims `remaining × indicator`, capped at the remainder, and softer tiers split what is left). Plain additive normalization was REJECTED after a screenshot: beside a city|dust wall with a grass wall within 150u, the dust side gave grass a third of the height and the city side (whose crisp window admits nothing) gave it none — a 1–40u SAWTOOTH CLIFF along the whole edge, and the server's walkers popped 5–44u a tick on it (heightfield vs analytic backstop disagreeing). With precedence the city's indicator is 1 at its wall on BOTH sides, so nothing else can leak in there, and `blend.test.ts` asserts the two sides of every city↔neighbor edge agree within 0.5u with no sawtooth along it. The shader mirrors the same tiers for the material (`combineBiomeMaterials` with `slotHalves`; `combineSlotWeights` is the JS twin the foliage uses).
- **`biomeSdf` is returned in its OWN buffer.** The flatten-pad step recurses into `computeVertexData` for pad candidates AFTER the outer vertex's wall pass, clobbering every scratch array; returning the scratch shipped a random candidate's distances to the shader for any vertex whose call built a flatten tile — jagged wrong-texture patches with black slivers (weights summing to 0) along edges, only "sometimes". Everything returned is captured before the pad step and the sdf is copied into `biomeSdfResult`, which the recursion (raw mode) never writes.
- **Heights are asymmetric.** Height = Σ weight × (that zone's REGION base noise + its biome height × its PRESENCE). Windows use each zone's `heightBlendWidth`, so a CRISP zone keeps its full height to the wall and the soft neighbor does all the ramping: the city (2u) holds its plateau, the grass beside it climbs from the freeway grade over 150u. The city evaluated OUTSIDE its zone (up to the neighbor's half-width) continues at the belt grade (`cityHeightOutside`), which its own rim already holds at the wall (the freeway ramp is 0 outside the belt centerline and the curb dip fades to 0 at the wall; the out-of-zone branch lives in `zoneBiomeHeight`), so there is no step anywhere on the profile. Verified numerically in `blend.test.ts` (2u steps ≤ 6u of height change across a region edge; material weights sum to 1).
- **Presence — a biome fades into its REGION'S BASE at its own edge.** Per zone, `presence` is the signed distance into the zone scaled by its `blendWidth` (`heightBlendWidth` for the height), 0 on the wall, 1 one width inside (`biomePresence`, per slot, shipped like the sdf in its own result buffer `biomePresenceResult` — same clobber hazard). The biome's HEIGHT contribution is multiplied by it, so the mountain's rock climbs out of flat snow over 220u and the salt flat sinks into the dunes over 200u; the shader mixes the region's `<region>_base_frag` into the biome's own frag by it (`vBiomePresence0/1`), so the base texture shows at every biome edge and the biome's own texture grows in. Presence SATURATES one width in, so a height that must keep rising toward a group's middle uses a DOME instead (`BiomeNoiseConfig.dome`, the mountain): the ground rises with the square of `domeDepthAt` (zoneBlend.ts) — each site's distance to its zone's nearest foreign wall, cached per cell, interpolated by a compact kernel over the sites around the point and smooth-min'ed under the wall distance so it is 0 on the edge. Joined cells have no wall between them, so a joined group is ONE massif whose summit is where the group is deepest; the raw wall distance was REJECTED as the depth — it made every cell a faceted pyramid (creases along the medial axis). Its window-consistency was MEASURED (identical across every grid-window border out to the deepest point, ~660u), so the kernel and the smooth min add no seam. Crisp zones (`heightHalf` ≤ `CRISP_HALF` = 2, the city) have presence 1 everywhere. A blend width must stay under half a biome cell (`gridSize` 500): presence peaks at the cell center, and the mountain's first 450u feather never got past 0.5 — 14u "peaks", MEASURED. Anything that must NOT fade with a biome (the inter-city freeway paint) is applied in `combineBiomeMaterials` AFTER the presence mix — painting it inside the grass frag gave a green road with faint lane lines beside the city, where grass presence is low.
- **The material feather uses the SMALLER side.** Per wall `materialHalf = min(a, b)/2` when the biomes differ (same biome on both sides = no material feather at all), so a crisp biome never smears into a soft one — this is what makes the city's edge a hard line against grass AND dust while grass↔dust fades over 300u. The shader receives NOT a weight but a per-biome-slot SIGNED DISTANCE scaled by that half (`biomeSdf`, two vec4 attributes, ±`BIOME_SDF_FAR` when no wall is in reach): signed distance interpolates linearly across a triangle, so `smoothstep(-1, 1, sdf)` in the FRAGMENT shader lands a 1–3u feather at pixel resolution even on 17.5u LOD2 quads. A per-vertex WEIGHT would alias into a sawtooth on any feather narrower than a quad, and the previous `flat varying int vBiomeId` dispatch (a per-triangle hard switch) was exactly the "staircase of single-biome triangles" and the "thin outline tracing distant walls" the screenshots showed — both are structurally impossible now: `combineBiomeMaterials` runs every biome's frag where its weight is visible and mixes by normalized weight; there is no biome id in the shader at all. Slot order = unique biome ids in region→biome order (`biomeSlotsOf`; `world/terrain/material.ts` asserts the committed regions agree; max 8 biomes — the overworld uses 7).
- **Far LODs CLAMP the blend fields** (`LODLevel.clampBlendFields`, LOD3–5; applied in TerrainRenderer's `writeSdf`): sdf to [−1, 1], presence to [0, 1] — exact at every vertex, since the shader's smoothsteps saturate there. Unclamped, a 210–3360u triangle spanning three zones (or mixing a ±`BIOME_SDF_FAR` vertex with a near one) interpolates EVERY slot below −1 inside it: zero weight sum, BLACK terrain (MEASURED: the black horizon patches, proven with a `weightSum < 0.02` → magenta shader probe). LOD1/2 must NOT clamp: the true distances are what put the city's 1u edge in the right place on a 4.375u quad.
- **Widths resolve biome → region → domain default**, level by level, with `heightBlendWidth` falling back to that level's `blendWidth` (so the city's `blendWidth: 2` is crisp in both; set `heightBlendWidth` to separate them). Defaults 300/300 (`defaultBlendWidth`/`defaultHeightBlendWidth`). Half-widths are floored at 0.5u (a zero window would make a wall's indicators sum to 0). The old `boundaryWidth`/`biometexture` region band and the `blendable` flag are GONE.
- **Foliage follows the weight, not the cell** (`foliage.worker.ts`, `biomeWeightOf`): blades dither out with the terrain material's weight for their biome, because a hard stop on the cell line under a 300u texture fade read as an edge. Spawn/dressing filters still key on the own-cell `biomeId` (a building must stand in ONE biome). The same goes for the riverbed: every plant thins to nothing over `RIVER_BED_PLANT_RAMP` (8 factor-1 units) of `riverBedDistance` ending where the bed fully covers the ground (`RIVER_BED_REACH − RIVER_BED_FULL_INSET`, one constant shared with the shader) — before, blades covered the whole sand bank down to the water. Its keep roll is a per-blade HASH (chunk seed × draw index), applied LAST: a skipped `rand()` draw would reshuffle every later blade in the chunk, and phase/tint make up the LOD fade key.
- **Sky weights** come from the same walls with the REGIONS' own blend widths (not the biomes'): the city's 2u feather must not snap the sky.
- Rejected/measured: a shared scratch `biomeSdf` buffer is returned per vertex (copy it — the terrain worker interleaves it immediately; a test that read two results after the fact saw the second overwrite the first). A candidate "nearest-wall pair id + weight" scheme was NOT built: at Y-junctions its pair identity flips discontinuously, which is the seam class the spec forbids. the belt freeway is CENTERED on the biome wall, so the road itself is the divider — its inner half the city's rim, its outer half graded and painted by the shared off-city freeway code (the belt enumerators step the wall itself and invert the warp). "Remove the perimeter freeway" from the original spec was read as MOVE it to the border: deleting it would dead-end every outbound arterial.

**Addresses — the URL is a place** (`src/world/domains/overworld/address.ts`, Three-free; `FastTravel.tsx` is the React glue). A path is `/<region words>/<biome words>` — `famous-sprawl/velvet-town` (a city cell in a city region), `amber-lakelands/twin-pool` (a lake), `deep-winterland/hushed-spire` (a mountain). BOTH the region-grid cell and the biome-grid cell get a name that is a BIJECTIVE ENCODING of its cell coordinates (zigzag → bit-interleave → the low 12 bits scrambled by a fixed odd multiplier → 8-bit ADJECTIVE words, then one 4-bit NOUN drawn from the THEMED list of what stands there: `REGION_NOUNS`/`BIOME_NOUNS` have a 16-word list per region type and per biome type), never a hash and never a registry: nothing is enumerated, a name nobody has visited decodes exactly. Names are TWO words within ±32 cells of the origin, three within ±512, four beyond; the noun decodes from ANY theme's list (`REGION_NOUNS`/`BIOME_NOUNS` keyed by name, `GENERIC_NOUNS` for the rest; every noun unique across all lists, asserted at load), so the theme only changes the word, never the place. Type forms: `/city` = the city region's cell nearest the world ORIGIN (ring scan of cell rolls — the same place for everyone), `/snow/mountain` = the mountain cell nearest that region cell's site; the CRT pages use them. Travel lands on the biome cell's voronoi SITE (warp-inverted to world space), lifted onto the water where the site is in a lake. **The wall NETWORK — freeways live on the biome walls** (`getNetwork` in `utils/workers/roads/freewayNetwork.ts`, cached per biome-grid cell). **Rivers — the edges of their OWN voronoi grid, and cities adapt to them** (`utils/workers/rivers/riverNetwork.ts` — its header is the design in one screen — the road layer `riverRoadLayer.ts` and the per-vertex `riverField.ts`). Rivers are the voronoi edges of a THIRD grid — `RIVER_GRID_SIZE` 2800, jittered sites shifted by `RIVER_GRID_SHIFT` (1237, 811) so it never lines up with the region grid — INDEPENDENT of biomes and roads: a pure function of position, so every chunk, window, worker and the server agree by construction. Three layers:
- **The network** (`getRiverSegments`, cached per river cell, `RiverSegment` pieces in warped space). Sites ±`RIVER_GRID_RADIUS_CELLS` (6) around the query's cell; edges reaching the cell ± `RIVER_TRUST_MARGIN` (2400) are emitted. Only TRUSTED triangles (circumcircle a cell inside the sites) make edges, and junctions are computed from their three sites in a canonical order: an edge is cached by its two sites, and one first built from a distorted border triangle kept wrong junctions for every later query — MEASURED as a chunk's decks changing with what had been queried before. Each edge rolls whether it carries a river: probability `RIVER_KEEP_PER_PROBABILITY` (0.78/0.45) × the `riverProbability` of the region under its midpoint (the domain's `river.defaultProbability` where a region sets none), capped at 1 — the 0.45 default keeps the old 78%, the desert (0.15) a quarter of its edges, snow/ocean nearly all; a domain whose probabilities are all 0 has NO rivers (home). Edges are cut into `RIVER_SEGMENT_LENGTH` (50u) pieces, and a piece is NOT built (1) `RIVER_MOUTH_REACH` (160u) deep into WATER cells in both directions along its edge — symmetric, so the mouth runs on into the basin and never depends on the walking direction; (2) where its pond-sized footprint would touch a `prohibitRivers` biome (probes run only if some biome sets it — none does today); (3) on HIGH or STEEP ground (Evan: uphill water) — biome relief > `RIVER_MAX_RELIEF` (40u, the mountain's rock), a grade over the piece and its neighbors > `RIVER_MAX_GRADE` (0.2; Evan raised it from 0.12), a RIDGE (centerline `RIVER_MAX_RIDGE` 6u above both footprint edges) or a HILLSIDE (the footprint's edges differing by > `RIVER_MAX_CROSS_GRADE` 0.15) — judged on a cheap terrain proxy (zone base + biome relief faded by the distance to the cell's edge; a real evaluation would need every biome cell's freeway network over a ~20km window). Only the RELIEF rule is final (`RIVER_BLOCK_MOUNTAIN`): a gap of grade/ridge/hillside pieces up to `RIVER_GAP_FILL` (800u) with river or water on both sides — a built piece, a water piece, or the edge's junction in a water zone — IS built (Sept 25 round 14, Evan: "ensure the rivers actually connect to their nearby bodies of water", screenshot: one river in three blobs between two seas; the desert's and the snow's own region bases exceed the grade and hillside limits, so the rules cut ordinary rivers everywhere — MEASURED over a 40 km square: gaps under 800u between two stretches 159 → 54, stretch ends under 800u short of the water along their edge 40 → 15, every one left touching the mountain's rock or a road-suppressed stretch; built pieces +24%); (4) in a stretch under `RIVER_MIN_STRETCH` (300u) between two unbuilt pieces (MEASURED: otherwise 197 of 363 stretches were pond blobs under 150u) — after the gap fill, and never one joining water to water. Every end of a built stretch where a piece is not built is a POND (`RIVER_POND_FACTOR` over the last `RIVER_POND_LENGTH` — a fatter capsule end); a junction no other BUILT river leaves is a natural end, a pond or a FIZZLE (`RIVER_FIZZLE_FACTOR` over only the last `RIVER_FIZZLE_LENGTH`), seeded per junction. WIDTH is per junction — ±25% jitter × (1 + `RIVER_OCEAN_BOOST` × nearness to the nearest all-water region site within `RIVER_OCEAN_REACH`), capped at `RIVER_WIDTH_MAX` — interpolated along each edge, so rivers widen toward the ocean. NOTHING IS CUT FOR A CITY: a version that cut rivers out of the city and dropped the stubs was REJECTED from a screenshot (blobs beside every city, a river ending 80u short of the sea); the city adapts instead. Two trace-based designs on the biome walls were REJECTED before that (window- and order-dependent: rivers ended at cell borders, sat inside city lobes, missed the sea).
- **The road layer** (`riverPieceSuppressed`; Evan: the road wins). Where a run, the belt or an in-city arterial runs within 35° of a river (`RIVER_ROAD_ALIGN_COS`) inside its footprint (+ the road's half-width) for `RIVER_ROAD_ALONG_MIN` (500u) or more — longer than a deck should be — that stretch is not built and the river ends BLUNTLY on either side (its last built piece keeps full width — a round capsule end), so the road stays dry. Crossings keep their decks: the angle gate is what keeps a GRID of separate crossings (the city's arterials) from reading as one long stretch (an angle-free "road inside the footprint" rule wiped the rivers out of whole cities). Lazy per piece — it needs the freeway network of the piece's biome cell — cached on the edge; skipped for edges with no city within `FREEWAY_LINK_CELLS` (no road can reach them).
- **The road layer's second half: no freeway severed** (round 16, `riverEdgeRoadLayer`; `riverPieceSuppressed(e, i)` reads it). Per biome cell, the pieces that survive the road layer within the widest possible reach, with the water SURFACE at both ends of each (`riverSurfaceAt`: the terrain at that centerline point — its own wall pass, the city at its plateau FLOOR (a surface hung from the freeway grade had blocks under it), lifted with a lake's shore — minus `RIVER_SURFACE_BELOW` 2.5, deeper than the lake's 1.5 so the quay road stays above the water — and near a lake EASED ONTO THE LAKE'S LEVEL over `RIVER_MOUTH_APPROACH` (250u) from its wall, never below it on land and never above it in the water: hung from the terrain alone, a mouth's surface stood ~11u over the lake at the wall and dropped to it over one 50u piece, a stepped, jagged sheet of water (MEASURED at famous-shallows; screenshot). In the water the channel stays sunk under the lake, or the bank rule would raise a levee across the lakebed). A piece end's surface also stands `RIVER_ROAD_CLEARANCE` (5u) under the lower landing grade of every run and belt crossing the two pieces beside it (`roadCrossingCap`, round 15, per piece end so neighbors agree): a river running along a ridge crest the road came through in valleys had its banks held up as a levee and needed a 43u arch, so the run got no deck (Evan, famous-meadow). Only the river comes down; roads, cuts and grades are untouched. The surface is interpolated along the piece: a function of the CENTERLINE only, so it is level across the channel (sampling the centerline with each vertex's own zone weights tilted it). The distance is measured from a MEANDERED query point (`RIVER_MEANDER_AMP/SCALE`, a straight edge winds) and NORMALIZED by the local width factor — `distanceToRiverCenter` is in FACTOR-1 units, so `river.halfWidth/depth/bank` (40/9/36) describe a factor-1 river and every consumer (channel, bank, bed paint, bridges, `riverKeepOff` filters) compares against them as is. Pieces of ONE river combine by a plain min (their joints never notch); DIFFERENT rivers by a compact smooth minimum (`RIVER_FILLET` 24 factor-1 units: weights h² with h = 1 − gap/FILLET), the width factor and surface weighted the same way, so confluences get a fillet and nothing jumps where the nearest river switches. The quay reads a second combination from the STRAIGHT (un-meandered) point — distance, width factor and direction all from it.

THE CHANNEL (step 4) is FORCED, not min'ed: a parabola from `surface − depth·√factor` at the centerline to a RIM at `surface + SHORE_RISE` at the half-width (the water's edge sits just inside), the bank blending the rim into the terrain over `bank` — raising low ground as well as cutting high ground (a min() alone left low far banks under the water). Water is drawn out to `halfWidth + bank/2` (the water band, past the waterline so the shore triangles are level), and ground LOWER than the rim is HELD at the rim across that whole band before it descends (`smoothstep(waterBand, reach)` instead of from the half-width): blending it down from the half-width put the bank under the surface, and the water mesh drew a second, stair-stepped strip on the dry bank (screenshots; the ring around a pond end was the same). The water mesh and the terrain share one grid and interpolate linearly on the same triangles, so the vertex-level guarantee — no vertex outside the channel reports water above its ground — holds across every triangle at every LOD (`riverBanks.test.ts`, LOD1/LOD2/LOD3 spacings; 2016 such vertices over four 3km squares before). In the channel the city's lane paint is blanked; the ground under a city deck is cut by step 7 like any. `passesPlacementFilters` rejects every object within `riverKeepOff()` (channel + banks) and on or beside a bridge deck (`underDeck` > 0 — a street lamp stood in the middle of a deck, screenshot; the dressing enumerators — markers, signals, poles — test it too), and foliage skips points under water. **Lakes, shores and the Water system** (`utils/workers/lakes.ts` + `computeVertexData` step 4 + `world/water/waterMaterial.ts` + the water child mesh in `TerrainRenderer.tsx`). LAKES are a biome with `water: { depth }` (the ocean region's lake biome, `joinable`, so adjacent lake cells are one body): the water sits at a LEVEL = the region base at the cell SITE − 1.5, BLENDED across every water cell within 1.5 cells by a compact kernel (`lakeLevelAt`) — one level per cell was MEASURED as 1–3u walls of water on the wall between two lake cells; the kernel's support fits inside the 5×5 grid window, so it never steps at grid borders. The lake's terrain is defined RELATIVE TO THE LEVEL, not the base: `level + SHORE_RISE` at its wall (presence 0, seen from either side) descending to `level − depth` at full presence. LAND NEAR WATER NEVER SITS BELOW THE WATER: any non-water vertex within `SHORE_CLAMP_FULL` (160u) of a water zone's wall is lifted onto `level + SHORE_RISE`, fading back to its own relief over `SHORE_CLAMP_FADE` (250u) (`shoreLift`, also applied inside `blendedTerrainAt` so a river surface or road grade sampled beside a lake is lifted with the ground around it) — the desert dipped 100u under the ocean's level beside it, a wall of water seen from the dunes. `VertexResult.waterHeight` (NaN where there is no water in reach) becomes a second mesh per terrain chunk — a child of the chunk plane on pooled geometry with a `waterDepth` attribute, sharing the chunk's lifecycle (`Chunk.water`, `releaseWater`) — drawn by `getWaterMaterial()`: swell in the vertex shader, two scrolling fbm normal octaves, fresnel, sun glint, depth-tinted color, alpha fading out over the last 2.5u of depth (a hard discard, and then a 0.6u fade, traced the LOD triangles as a staircase along every shore), night dim; dry vertices of the water mesh dive under the ground by at least the vertex spacing (3u let one wet vertex of a coarse LOD — a river is narrower than its quads — spread a water sheet over the banks until LOD1 arrived); `tickWater(clock)` from TerrainRenderer drives the time. Foliage skips submerged points and points under a deck (`underDeck`), and the terrain grade of a freeway does NOT flatten a channel (that is what the bridges are for). Physics does not know water: the player walks the riverbed and lake floor (swimming is open).

**Inter-city freeways and bridges** (`getNetwork` + `computeVertexData` step 5; paint in `combineBiomeMaterials`; `objects/dressing/bridges/`). FREEWAYS ARE A SET OF WALLS, walked out into polylines (`FreewayRun`: warped points + cumulative arc length + dash phase + bounding box): (1) adjacent city cells form one CITY (union-find over city|city walls — one road per pair of neighboring cities, never one per cell pair: per-cell straight runs gave three near-parallel roads out of one city and one skimming its belt), and every pair of cities within `FREEWAY_LINK_CELLS` (4) gets the SHORTEST PATH (binary-heap Dijkstra, ties broken by junction position) over walkable walls (no city, no water and no `prohibitRoads` biome on either side — the lake sets it; rivers live on their own grid and cross roads freely, see the rivers paragraph) from a junction on one city's boundary to one on the other's — a third city's junction is forbidden (it relays), a path longer than `FREEWAY_PATH_MAX_STRETCH` (1.7) × the straight distance is dropped, and so is any path touching the window's untrusted border; (2) GAP HOPS: every walkable chain of ≤ `FREEWAY_GAP_WALLS` (2) walls and ≤ `FREEWAY_GAP_LENGTH` (450u) between the boundaries of two DIFFERENT city cells with no city junction in between — the short grass gaps between lobes of one city (a screenshot circled three). Shared walls merge, hubs form where chains meet. Every run starts at a wall junction, i.e. a corner of the BELT, which is CENTERED ON THE WALL: its inner half is the city's rim, its outer half rides the neighbor biome — grass, dunes or a LAKE (a causeway on the city's grade above the water) — so the two roads meet as one network node with no gap and no material change (the inset belt whose outer lane edge sat on the wall met every run across a strip of grass). Step 5, for every non-city vertex: the nearest of {run, city wall} (`nearestFreewayRun`, `findNearestCityWall`) is the ROAD; within `freewayWidth + FREEWAY_GRADE_RAMP` the terrain rides the GRADE — ONE per centerline point, a pure function of the road (`freewayGradeAt`, round 17, Evan's 59/60: under the VERTEX's own zone weights the two halves of a run lying on a biome/region wall rose to different grades, a crease down the middle): the terrain at the centerline point with ITS OWN wall pass (`terrainOnlyAt`, the city at its rim grade), sampled on an 8u lattice per segment (cached, exact-keyed — a `toFixed` key made it order-dependent), smoothed along the run over 5 taps (reflected past its ends so two runs agree at a hub), blended over nearby segments by distance and over one run's legs by ARC, the warp's shear corrected so the cross-section is square in the world — flat across, dipped `curbHeight` inside `roadWidth` exactly like the city's field, ramping back over 10u EXCEPT where the road YIELDS to a river — across the whole footprint for the belt's outer half (its inner half is the city's, which the quay yields there), only within `runRiverYield()` (the water band + 6) for a run, blended where the two meet — so the water stays open under the road and a run grazing a bank or a pond stays a road; the ground under an actual deck is cut by step 7 (see BRIDGES below). `distanceToRoadCenter` (normalized street units, 99999 off-road — it no longer starts at the biome-boundary distance) is written continuously out to `FREEWAY_FIELD_REACH` (70u): the shader's corridor mask interpolates it per vertex, and a 99999 beside a 9 aliased the corridor's edge into the triangle grid. BRIDGES are DRESSING (`Bridges.tsx`, spec in `bridgeSpec.ts`, material in `deckMaterial.ts`; enumerator `getFreewayBridges`, the `bridges` entry of the dressing enumerator table, which skips the city probe; the header of `utils/workers/bridges/freewayBridges.ts` is the design in one screen). THE GOAL, stated once: a road that genuinely CROSSES a river is carried on a deck from dry road on one side to dry road on the other, continuous with the road network and reading as that road (same asphalt, lane paint, square flush ends), and nothing else gets a deck — Evan, from the river-mouth screenshots (decks along the shore, V meets mid-river, wedges, stubs between decks): "change the rules to avoid situations like this". Roads and rivers are both analytic, so decks are computed GEOMETRICALLY (v1 marched the terrain from each crossing with attach/continue heuristics — slow, and decks still ended in water at path seams; an angle-based span before that ended one crossing's deck inside the next crossing's water): (0) WINDOWS: a chunk looks at ±`BRIDGE_WINDOWS[0]` (900u, warped) around its center; every interaction a chain has with what lies outside it (a wet stretch merging on, an end meeting another, a tee) is within `BRIDGE_EDGE_GUARD` (48u), so a chain with a sample that close to the window's edge is UNDECIDED there — a query whose decks depend on one (a host, a child, an overlapping deck) retries with 1800 and then 3200, where an undecided chain drops (`window`). Chains longer than `BRIDGE_MAX_LENGTH` (1000u) drop whatever the window, which keeps every owned chain ≥ the guard inside the first window (midpoint ≤ 181 + L/2 + the warp's 150u spread + 48 ≤ 900) and a T closure two chains deep inside the last. A single ±800 window was MEASURED to split T-junctions across chunks; one ±2200 window fixed that at ~100× the per-chunk cost. Roads are CLIPPED to the window, not required whole, and the belt's loops, chains and seams are all canonical (smaller end first, seam at the node the river field says is driest, ties by position). (1) `RoadPath`s — only the road within `BRIDGE_ROAD_MARGIN` (60u) of a footprint, inside the window: the network's RUNS, the BELT (city walls with the city on exactly one side, each from the biome cell holding its midpoint, network-free via `getZoneWalls`, chained by endpoint; a closed loop is opened at its node farthest from the rivers), and in-city ARTERIALS (`collectArterialPaths`). Samples sit on CANONICAL lattices — each wall from its own lexicographically smaller end, the arterials on a global 8u coordinate lattice — so every chunk samples a road identically. (2) WET = the terrain's own river field at ANY point of the road's CROSS-SECTION (the centerline or either deck edge, ±W/2), against the distance the terrain yields that road at: the whole footprint (`halfWidth + bank`) for the belt and the arterials — the quay yields there — but only `runRiverYield()` (the water band + 6) for an inter-city RUN, which stays a road on a river's outer bank or beside a pond (step 5 uses the same numbers, so a deck always covers every vertex whose road the terrain gave up; a centerline-only test left a wedge of the road's curbed end showing past an oblique deck's end). A maximal wet stretch (gaps < `BRIDGE_WET_MERGE` 16u merge) is one `WetItem`, extended by the abutment onto the dry road beside it (LANDED ends) — or OPEN where the road itself ends while wet. (3) JOINS: open ends within `BRIDGE_END_MEET` (10u) form a node; its straightest pair continues through as one chain ONLY if nearly straight (directions into the two items ≥ 145° apart, `BRIDGE_JOIN_STRAIGHT_COS`) — two roads meeting at an angle joined into one V-kinked deck; every other end tees onto a road PASSING the node (its item continuing ≥ W/2 either way — "T"s onto another road's end overlapped as wedges) within `BRIDGE_JUNCTION_REACH` (6u), or its chain drops. THE CUT follows the DRAWN slab (`bridgeDrawnAt`: `bridgeSections` quads inverted by Newton, cached per deck with per-quad bounding circles), not the centerline: under it and beside it out to `deckCutMargin` = the chunk's vertex spacing × √2 + 0.5 (a triangle with a vertex beyond the slab still spans it — image 49; the terrain worker sets it per chunk with `setDeckCutSpacing`, the server/main thread keep LOD1's), to the least top the vertex's triangles can reach, above any water. The overlap query that feeds it (`getFreewayBridgesNear`) pre-filters an unresolved mouth crossing by its box + 0.7 × `MOUTH_PAIR_MAX` (its box covers where the deck is MIDPOINTED; a lone mouth's far end was never cut). A LANDED CUT END (`landedCut`: the end section along the road's edge at the ASPHALT height of its corners) is flush with its road: in front of it the road is held at the cut's own cross-fall carried on at the centerline's pitch (`bridgeDrawn.flush`, BRIDGE_CUT_FLUSH), its MOUTH (`bridgeMouthAt`, BRIDGE_MOUTH_DEPTH) is asphalt at that height (no curb across the deck), and the cut's cross-fall eases into the deck's own over `BRIDGE_CUT_TWIST` (12u — the next section was flat, and on a hillside road the slab's edge dropped 3u within a unit of its cut; 24 dipped a low edge under the water). A T end on a corner its host's deck rounds is carried on along its last leg onto the host's centerline (`extendOntoRoundedHost`, ≤ 16u; the chain's midpoint is kept). A fill/arterial/lone-mouth STRAIGHT crossing may run ≤ `BRIDGE_MAX_ALONG_SHORE` along the river inside its footprint (`straightAlongShore`: a fill slot at a bend ran 300u along the other leg's bank). `MOUTH_PAIR_TURN` stays 50° (65° paired a belt corner with a belt running along the far bank: the deck's approach lay over that belt and cut it). A run whose end corner's belts all hit water within 40u is a STRANDED run end and gets a mouth of its own (`strandedRunEnds` — 43.png: the run's only way on was the drowned belt). A both-landed chain kinked past `BRIDGE_MAX_TURN` is tried as one Hermite curve tangent to its end legs before it drops (`smoothKink`). Deck clearance is checked at the centerline AND both edges.

**Heights have a single source of truth**: `src/utils/workers/vertexCompute.ts` (`computeVertexData`, over its sibling pipeline modules — see the Directory Layout) is the ONLY height implementation, and the one module every caller imports the pipeline from. The terrain, spawn, foliage and dressing workers run it off-thread; the main thread (`src/world/terrain/vertexData.ts`, used by Player respawn and by the address resolver — `ensureVertexCompute()`) imports and runs the SAME module, initialized with the same serialized `DomainConfig` from the active domain. Biome heights are defined declaratively by the biome spec's `noise` (registered by `<Biome spec>`, read by config.ts); biomes with bespoke height logic (city — block plateaus riding the regional base noise) have their branch in the pipeline (`zoneBiomeHeight` → `roads/cityTerrain.ts`). Never add a second height code path.

**Flatten-ground pads** (`flattenGround: true` on an ActorSpec — buildings, future houses, ANY biome): the terrain flattens a PAD under every instance — flat at the actor's raw ground height inside `flattenRadius` (default footprint × 0.45), blending back over `flattenSkirt` (default footprint × 0.35). The chicken-and-egg (spawn points come from terrain height; terrain depends on spawn points) is resolved by making these actors' placement FULLY DETERMINISTIC: the flatten engine (`utils/workers/flattenPads.ts`) rolls the exact spawn.worker density seeds/filters per canonical 128u tile with ITERATED LOCAL spacing (Matérn-II rounds: reject on any earlier-ordered POOL member within own footprint, then let rejected-but-viable candidates re-enter against the actual winners for FLATTEN_SPACING_ROUNDS rounds — a single round was tried and REJECTED: it saturates at ~45% of greedy packing and visibly thinned the city; plain greedy-vs-accepted was also REJECTED: acceptance chains cross tile windows and tiles disagreed. Round-k locality = k×footprint, covered by the spacing window pad), and BOTH the height function (`applyFlattenPads`) and spawn.worker (`getFlattenPoints`) consume that one function, so every instance sits exactly on a pad. Pad candidates evaluate filters against the RAW pad-free height (`evaluatingPadCandidates` guard; `computeVertexDataRaw` for sparse scans/tests — a coarse scan through the padded path computes a pad tile per lonely sample), and pads only activate in biomes some flatten descriptor targets. Set `biomeIds`/`density` etc. on the biome spec's `actors` mount — the client registration AND config.ts's flatten list both derive from it (see the grass biome's `GRASS_BUILDING_SPEC`: a distinct id, since descriptors dedupe by id and "building" belongs to the city). PERFORMANCE (each pad candidate costs one raw height evaluation, per worker): (1) far VISUAL-ONLY terrain LODs skip pads entirely (`visualOnly = !lod.hasCollider` → `computeVertexDataFar` — a LOD5 chunk spans ~256 pad tiles and builds exploded ~9×, stalling terrain and therefore spawning; collider LODs keep pads so physics matches; the same path also skips the freeway RUNS, and at LOD4–5 the river field, see Performance Notes); (2) the player's frequent ground checks use `getVertexDataRaw` as a cheap PRE-FILTER only, and the padded CONFIRM runs in the dressing worker (`getVertexSample`, re-exported from `world/terrain/vertexData.ts`) — a padded lookup that misses its flatten tile costs ~30–70ms, which the worker absorbs instead of the frame; one-off callers like respawn keep the main-thread padded path. Raw height is NOT a lower bound on the real surface: pads EXCAVATE as well as fill (the height lerps toward the actor's ground height), so uphill of a building on a slope the true ground sits BELOW raw — measured up to 8.3u, past the backstop's 2u tolerance on 6% of pads. Any below-surface test must CONFIRM with the padded height before acting (`resolveEmbeddedSurface` in Player.tsx); trusting raw alone made the fall-through backstop teleport the player out of a building's excavation every 3 frames, an infinite bounce when sliding into a building on a slope; (3) candidates are cached per cell across tiles (overlapping tile windows re-evaluated boundary cells ~2.2×); (4) overlapping pad influences apply in ascending mask order so the dominant pad keeps its flat zone exact even when a dense neighbor's skirt reaches in.

**City terrain** (`utils/workers/roads/cityTerrain.ts`, tuned via `cityConfig` in `world/defaults.ts`): the city is partitioned into large STAGGERED DISTRICTS (jittered rows ~`districtSize` cells tall split into staggered jittered segments — sizes ~0.6–1.4×; `cityDistrictByIndex`), and EACH DISTRICT ROTATES its entire block grid by a seeded multiple of 15° (15°–75°; 0° is deliberately excluded so every district reads as rotated) about its own center (`getCityTerrain` transforms the vertex into the district-local frame; distances/heights are rotation-invariant so nothing needs back-transforming). District boundaries carry the ARTERIAL roads (`freewayWidth` half-width, normalized into street units like everything else) and are WIGGLY — each boundary bends with two seeded sine octaves (`cityWiggle`, amp `CITY_WIGGLE_AMP`), and district ASSIGNMENT follows the same curve so the rotated-grid frame switch always stays buried under the arterial surface; arterials also absorb the seams between differently-rotated grids, and block plateaus ramp to the shared MID-PLATEAU FREEWAY GRADE (maxBlockElevation/2, spread over `CITY_FREEWAY_RAMP_START` 14 → `CITY_FREEWAY_RAMP_END` 34u, both past the lanes so a freeway is flat across its four lanes — grade 0 with a tight ramp was rejected: every freeway read as a V trough) at arterials so elevation stays continuous across districts. Arterial markers follow the curve, oriented along its tangent (`cityWiggleSlope`). Within a district the layout is a square BLOCK GRID (`gridSize` per cell; NOT voronoi — a voronoi partition was tried and rejected as too round/organic) — each cell rolls a block index in `[0, blockCount)` (cached per cell in `getCityCell`, seeds salted by district key; −1 near the biome wall = whole cell is the rim ring road, plateau 0); neighbors that roll the same index merge into larger polyomino blocks. (1) STREETS run along boundaries of differing-label cells, computed as boundary SEGMENTS over the full 3×3 neighborhood rather than per-cell infinite lines — segments entering/leaving the set at a cell border are always ≥ ~half a cell away, keeping the field AND the s1+s2 chamfer continuous (per-cell line constraints were tried and REJECTED: the chamfer's second constraint popped identity at cell borders, leaving jagged notches in road edges). Contiguous collinear segments along one boundary line are MERGED into single runs before being considered — otherwise a straight road along two merged same-label cells is two collinear segments and the chamfer pairs them (two pieces of the SAME road), undercutting the field and notching the sidewalk at every merged-block cell seam; (2) SHAPE FEATURES rolled per 2×2 SUPER-CELL in `getCityCell` (each replaces FOUR normal blocks) — TRIANGLE super-cells (`triangleChance`): one unique label across the super-cell (boundary streets guaranteed) with a corner-to-corner diagonal road splitting it into two large flatiron halves that always terminate in intersections; ROUNDABOUT super-cells (`roundaboutChance`): a large circular block (island) inside a ring road centered on the super-cell — member cells COPY an outward neighbor's label (`baseCityLabel`, non-recursive), so the wrap-around blocks outside the ring MERGE seamlessly with the surrounding grid (only the ring road separates them from the island); internal member boundaries whose copied labels differ become the streets radiating from the roundabout — inside the ring, boundary constraints are suppressed (the toggle hides under the ring road) so those streets tee into the ring instead of crossing the island, and the island's height is overridden to its own flat plateau (blended in under the inner ring road). The island's field is compressed ×0.75 so buildings keep a safe margin from the curved curb. Features only spawn when `superCellHasRoom` passes — the whole super-cell must be clear of the biome rim AND of the district's arterial boundaries, so no half circles or clipped diagonals at boundaries. Features are CONFINED to their own super-cell — the core no-tiny-pieces guarantee (cross-block avenue lattices were tried and REJECTED: lines crossing many blocks manufacture fragments). The biome RIM is a BELT FREEWAY — a freeway ring surrounding the whole city that the outbound arterials empty into, and it IS the city's border: its centerline sits ON the biome wall, so its inner half is the city's rim and its OUTER half is graded, dipped and painted by the shared off-city freeway code (computeVertexData step 5 + the terrain shader's `city_frag` corridor — see "Inter-city freeways and bridges"); the inter-city runs leave from its wall junctions, so a run and the belt meet as one road-network node. Inside the city it is fed into the road field with the freeway normalization + a recovery that starts at `CITY_BELT_RECOVER_NORM` (earlier than an arterial's, so blocks stand near it), at the same mid-plateau grade with the full curb dip up to the wall (the neighbor side dips by the same formula), and dressed EXACTLY like the other freeways: dashed lane lines (dash phase = the biome-wall projection — the same `along` the outside computes, so the phase is continuous across the wall) and median raised markers (enumerated by stepping the city's wall segments in warped space and INVERTING the road-noise warp by fixed-point iteration (`unwarp`); validity filtered through computeVertexData — not by biome, a marker on the centerline may fall a hair to either side of the wall; getWalls emits each wall twice endpoint-swapped, so only the canonical orientation is processed); blocks melt/chamfer against it like any road, rim −1 cells only trigger basically ON the boundary (`gs × 0.15`), and street markers stay clear of the belt corridor; (3) ARTERIALS — the district boundary roads described above (there is no separate freeway lattice anymore), normalized into street units (× `roadWidth / freewayWidth`) so ONE road field drives the shader bands, curb dip, and spawn filters (arterial features just render stretched). The normalization only applies through the visual bands: past `CITY_ARTERIAL_RECOVER_NORM` (12.2 normalized, just beyond the interior-band start) the arterial constraint RECOVERS at `CITY_ARTERIAL_RECOVER_SLOPE` (steep) via a continuous max() of the two slopes — without the recovery, the squash held the field below the building-spawn threshold for ~11×roadWidth real units and left the blocks along every arterial empty; with it, buildings reach a near-normal setback (~21u) from the freeway curb. The road field is min over all constraints — pure closed-form arithmetic per vertex (cached cell lookups + a handful of line distances), no voronoi/Delaunay; a RIVER through the city adds a QUAY ROAD constraint along each bank (see the rivers paragraph). Where a city wall running ALONG a river lies in its footprint (its belt's river-side curb in the water; `wallDrownedAt`, sampled along each wall per river list, only walls within 30–50° of the river — a belt CROSSING a river is decked, not drowned), the BELT is carried on the water's straight edge as the WATERFRONT (`findWaterfrontBelt`, round 15, Evan: "the freeway perimeter of the city should continue along the edge of the river"): the drowned wall's belt distance is pushed off by `CITY_WATERFRONT_PENALTY` and a line at bank + freewayWidth from the river takes over, joined by a smooth minimum (`CITY_WATERFRONT_FILLET` 30u, a rounded corner where the belt comes out of the water) — one road, one set of belt lanes (its paint never "ends" at the river), its river-side curb on the bank; off the city the drowned belt's half yields by the straight river distance too and keeps no paint, and rim cells beside a drowned wall are blocks, not all-road. A widened quay was tried first and REJECTED (two dash sets crossing, a plaza). Constraints are collected with their toward-road unit DIRECTIONS (world frame; rim = NaN, pairable with anything) and feed a fully PAIRWISE linear chamfer/melt: `min over pairs of (dᵢ + dⱼ + penalty) × CITY_CHAMFER_SCALE` — block corners at intersections get straight 45° cuts and fragments pinched under ~`roadWidth / scale` span become road entirely. The penalty fades in smoothly (`CITY_CHAMFER_DOT_LO/HI/PENALTY`) as the two directions align: inside a corner wedge or pinch they are ≥ 90° apart (no penalty), while a road event ACROSS the street — a T-junction stem or far-side bend — points the same way as the near road and must NOT notch the block edge (pairing s1-with-s2 without the direction test was tried and REJECTED: it bit cutouts into straight edges opposite every T-junction). Kept LINEAR and fully pairwise deliberately (a smoothstep-SCALED melt bends band contours into blobs; argmin-based pairing switches identity discontinuously). Each block index has a seeded plateau elevation in `[0, maxBlockElevation]`; elevation is bilinear plateau interpolation toward the neighbors the vertex leans into, ramping across street AND sidewalk (roadWidth + CITY_RAMP_SPAN each side) where labels differ. The city RIDES the regional base noise; flat building footing comes from the generic FLATTEN-GROUND PADS, not from the city (whole-block leveling via flood-filled polyomino anchors was built and REVERTED in favor of pads — pads work in every biome), avenues/freeways don't move plateaus (they just carve road surface across flat tops), and the road surface dips `curbHeight` below the sidewalk. `cityConfig.roadWidth` (7) is the street HALF-width (centerline → curb) and must match the band constants in the city fragment shader, which paints asphalt + gutters (0–7), curb strip (7–8), sidewalk (8–12), and plaza-concrete block interior (12+), plus fake directional shading from `vWorldNormal` so ramps/curbs read on the unlit terrain. FREEWAYS (`freewayWidth` 14 = 2× streets) are 4 LANES: raised markers stud the median, and each side splits with a white DASHED painted line at ±freewayWidth/2 — drawn from `vDistanceToFreewayCenter` (REAL-units distance to the nearest freeway centerline, arterial edge OR belt; 99999 outside the city and in JUNCTION ZONES — wherever a second freeway feature is within `freewayWidth + 10` — so paint ends cleanly before interchanges) plus `vFreewayAlong` (the dash-phase coordinate: axis coordinate for arterials, biome-wall projection via `lastWallAlong` for the belt), both plumbed VertexResult → terrain.worker → TerrainRenderer attributes → vertex.glsl varyings → city fragment shader because the shared normalized road field cannot distinguish freeway surface from street surface. CRITICAL: both varyings JUMP between adjacent vertices at wall-segment seams / axis switches / mask boundaries, and interpolation would sweep mod() into ZEBRA-STRIPE artifacts — the shader's fwidth() guards (a core GLSL ES 3.0 builtin under WebGL2 — three ≥ r158 has no `extensions.derivatives` flag to set) detect those slivers by their absurd world-space gradient and drop the paint there; do NOT paint from a phase varying without this guard. NO painted centerline — road centers get RAISED PAVEMENT MARKERS instead (paint shimmered): `objects/dressing/road-markers/RoadMarkers.tsx` (mounted in the city biome) builds one InstancedMesh of unlit yellow studs per 256u chunk, no colliders; positions come from `getCityRoadMarkers` in `utils/workers/roads/cityFeatures.ts` (via the dressing worker — `dressingWorker.ts`), which enumerates grid boundaries (owned by midpoint bounds) and lattice lines (markers on a global parameter lattice) — both duplicate-free across chunks — insets markers away from intersections, and filters per-marker by biome/river/on-road-center checks. Spawn placement uses the `roadDistanceRange` descriptor filter (also in normalized street units): buildings `[23, ∞)` / skyscrapers `[28, ∞)` (block interiors only — densities are raised to offset the smaller candidate area; footprint spacing is the packing limiter), street lamps `[8.2, 11.8]` (the sidewalk band).

**Performance note:** this is a *declarative shell* over the same pipeline as before — all heavy work still runs in web workers, and worker configs are built once at commit. Workers are initialized with the first committed config; registrations added after the first commit update the accessors but do not re-init running workers — a DOMAIN SWITCH re-inits them by termination (`resetDomainSystems()` runs between the old domain's unmount and the new one's mount, so the fresh workers lazily boot from the new commit).

### Terrain Pipeline

1. Player position → `computeDesiredChunks()` (quadtree LOD)
2. New chunks queued → `buildChunk()` async generator
3. Per-vertex: `computeVertexData` (or its raw/far variants). The full ordered journey of one vertex — every height step (warp, zones, city, lakes/shore, river carve, freeway grade, pads, deck cut, fragments), what each overrides, the uploaded attributes and the fragment shader's mix order — is [`src/world/VERTEX_JOURNEY.md`](src/world/VERTEX_JOURNEY.md)
4. Geometry buffers written, normals computed, skirt vertices set
5. LOD swaps CROSS-FADE (`lodSwaps.ts`, `LOD_FADE_SECONDS` 0.35): when every replacement of a component of old chunks is built, the old and new chunks are drawn TOGETHER with a complementary screen-door dither — new chunks keep the pixels whose screen-door threshold (`world/shaders/lodFade.ts`, the objects' 4×4 Bayer pattern) is in [0, p), old ones [p, 2), one progress p — then the olds are destroyed. Each pixel is drawn by exactly one of them (no hole, no z-fight, no double water: the water child uses the same range), and each threshold value sees a complete tiling, so skirts cover exactly as a static tiling. A fade whose old chunk is desired again runs BACKWARDS; a fading chunk never starts another swap until its fade ends; a swap whose old and new chunks cover different areas is instant (as before). Chunks mid-fade draw the terrain's FADE TWIN (`createLodFadeMaterial`, the `TERRAIN_LOD_FADE` define): `discard` in the one opaque program would cost every terrain fragment its early depth test, so only fading chunks pay it; the twin's program is linked during the load by a zero-area warm mesh. Colliders keep their lifecycle (built with the chunk, removed when it is destroyed), so the old ground lingers ≤ 0.35s longer; physics never sees the fade

### Actor Spawn Lifecycle

(The ACTOR class only — dressing has its own, simpler lifecycle: whole chunks mount/unmount around the camera, see `src/objects/dressing/Dressing.tsx`.)

Deterministic spawn points come from `spawn.worker.ts` (per-descriptor density grid + probability roll + spatial-hash spacing, cached per 250u chunk; cache entries carry their world-space CENTER and their spatial-hash membership, so the eviction sweep is a distance test rather than key parsing, and evicting a chunk also removes its points from the spatial hash — stale copies would otherwise block their own deterministic regeneration when the player returns). Delivered chunks are ALSO cached client-side (`spawnWorker.ts`), so the pool's every-5-frames batch only round-trips the worker for chunks it hasn't seen — steady-state batches serialize nothing over postMessage; `cleanupSpawnCache` evicts both caches with the same radius rule. `ActorPool.tsx` mounts/unmounts them with a size-aware multi-radius hysteresis:

- `immediateRadius = spawnRadius * 0.5` (or `desc.immediateRadius`) — inner zone: initial spawns allowed, REspawns blocked
- `spawnRadius = renderDistance + footprint/2` — points inside it mount (big objects spawn sooner); between immediate and spawn radius, respawns are allowed so a camped area keeps repopulating as NPCs wander off
- `despawnRadius = spawnRadius * 1.2` (or `desc.despawnDistance`) — mounted objects beyond it are unmounted by the pool sweep; the pool also passes radii to spawned components (`renderDistance` prop = fade start, `despawnDistance` prop = self-despawn hard kill) so all radii have one source
- **Initial spawns have NO inner exclusion zone** — a point newly entering the spawn radius mounts at any distance, so spawning catches up when the player outruns spawn batches
- **Only REspawns are blocked, and only in the immediate radius**: when an object self-destroys (`onDestroy` — NPC walked away, fade-out kill), its id enters a despawn ledger; the entry clears (after a 1s cooldown) once its spawn point is outside the immediate radius, allowing the respawn. Nothing is ever permanently despawned, and ids are position-based so an object can never be duplicated.

### Key Patterns

- **Declarative hierarchy, data-model core** — content is declared as JSX (each domain's `domain.tsx`), but the commit produces a plain `Region[]`/`Biome[]` data model (`src/world/types.ts`). Non-React code reads it from the active-domain accessors (`src/world/domains/utils.ts`: `getActiveRegions()`, `getActiveDomainConfig()`, `await whenDomainReady()`).
- **Hierarchy ownership rule** — code lives at the level it belongs to: biome-specific things in the biome folder, region-specific in the region folder, domain-specific in the domain folder; only genuinely shared systems live above the domains (world/, objects/, utils/, lighting/, vfx/).
- **Pattern files** — folders keep their data/config in consistently named files: `types.ts`, `constants.ts`, `defaults.ts`, `utils.ts` at the appropriate level (e.g. `world/types.ts`, `world/defaults.ts`, `world/domains/constants.ts`). No grab-bag singleton modules.
- **Every object extends its class base** — the load-bearing rule of `objects/`. Descriptors/props extend the attribute hierarchy in `objects/types.ts` (`GameObjectAttributes` → `ActorAttributes`/`DressingAttributes`/`FoliageAttributes` → member attributes like `ModelActorAttributes`/`BuildingAttributes`); an ACTOR is a `<ModelActor>` or uses `useActorLifecycle` (`actors/Actor.tsx`); DRESSING uses `useDressingChunks`/`useDressingAssets` (`dressing/Dressing.tsx`); FOLIAGE is `createFoliage(defaults)` (`foliage/Foliage.tsx`). Actor variants spread a base descriptor (skyscraper); an actor the server simulates is described FROM its Three-free spec (`describeActor(SPEC, {…})`, listed in `actors/catalog.ts`); group components come from `createDefaultsGroup`. Shared behavior goes IN the base — if you are about to apply a world-wide effect inside one object's file, that object is bypassing its base.
- **Specs are data, JSX renders them** — everything the server's config needs (ids, names, noise, flags, blend widths, biome order, a biome's `actors`) lives in `spec.ts`; `<Regions>`/`<Region biomes>` render component maps IN SPEC ORDER, so JSX and config cannot drift.
- **Scope-aware config components** — `<Material>`, `<Skybox>` mean different things under `<Domain>`, `<Region>`, or `<Biome>` (they read `RegionContext`/`BiomeContext`); `<Terrain>` is domain-only. Registration components render `null`; visual components (e.g. `GrassField`) render normally.
- **Registration effects use stringified deps** — inline object props (noise params, descriptors) are registered under `JSON.stringify` deps so parent re-renders don't re-commit the domain.
- **Utility namespaces** (material patchers + texture loading only): `_material.loadTextures()`, `_quantization`, `_curvature`. Math helpers are plain exports (`seedRand`, `smoothstep` from `utils/math/_math.ts`)
- **Worker clients extend `createWorkerClient`** (`utils/workers/workerClient.ts`) — never hand-roll a pending map / INIT handshake / terminate; a client file is only its typed request wrappers. Workers construct lazily (the collider worker no longer boots at module import).
- **Density placement has ONE implementation** (`utils/workers/densityGrid.ts`); the spawn worker, flatten-pad engine and dressing worker call it — that is what keeps pads under buildings. `passesPlacementFilters` also rejects every point within `riverKeepOff()` (channel + banks) of a river for EVERY object — the quay strip's capped field sat inside the lamp band, so lamps stood on the sand and in the water.
- **Plain utility exports**: `getAllBiomes()`, `getDistance2DSq()` from `src/utils/utils.ts`
- **Biome shaders**: each biome/region fragment shader becomes a named function; `combineBiomeMaterials` mixes them per pixel from the `vBiomeSdf0/1` / `vBiomePresence0/1` varyings (there is no biome id in the shader); the vertex shader is shared
- **Geometry pooling**: `acquireGeometry()`/`releaseGeometry()` recycle BufferGeometry per LOD level
- **Time-budgeted terrain builds**: chunk builds run until a wall-clock deadline (`BUILD_BUDGET_MS` in `TerrainRenderer.tsx`, ≥1 chunk per pass) with nearest-first re-sorting against the current camera — a vertex-count budget was replaced because per-chunk cost varies >10× with LOD/terrain
- **Voronoi caching**: grid results, Delaunay triangulations, and wall lists are all memoized on grid-array identity (`delaunayCache`/`zoneWallsCache` WeakMaps; the network per grid lazily in `networkByGrid`); boundary classifications cached with spatial eviction. The wall lookup used to rebuild the wall arrays per VERTEX — never regress this, it was the dominant chunk-build cost. SITES are cached per cell too (`rawBiomeSiteAt`: site + biome roll; `regionSiteAt`: site + region), in nested numeric maps: three `seedRand` calls per site per grid build were most of what a miss cost, and a network window re-reads 1369 sites, 97% shared with its neighbor's. The biome grid is looked up BEFORE its region grid (the region grid used to be resolved, key string and all, on every vertex), and keeps its old retention (grids > 5 cells from the latest miss drop) because the wall memos and `getZoneWalls`' sides cache were tuned under it; `getZoneWalls` sweeps that sides cache once per build (exactly equivalent to the old sweep per new label). MEASURED: a network miss 56 → 17 ms, a river-cell miss 91 → 25 ms, and the terrain worker's whole startup ring around a city spawn (228 chunks, every LOD) 90.8 → ~12–15 s of worker time — `NETWORK_CACHE_MAX` 48 → 1024 was half of it (the ring touches ~720 cells and rebuilt 1331 networks at 48; ~10 KB each).
- **DomainConfig**: serializable config sent to workers (`buildDomainConfig(regions, params)`, `world/domains/buildDomainConfig.ts`) containing region/biome data (with per-region base noise + riverProbability, per-biome water, per-level blend widths), global terrain params (from the domain-level `<Terrain>` — incl. the river config), per-biome noise (from the biome spec's `noise`), flatten descriptors (from the biome specs' `actors`), and city config

## Adding Content

### New Region (the normal way to add a "world": a new zone inside the one map)

1. Create `src/world/domains/overworld/regions/<name>/` with `spec.ts` (`RegionSpec`: a unique `id`, a unique lowercase `name`, `biomes` in VORONOI order, its `baseNoise`, `riverProbability`, optional `blendWidth`/`heightBlendWidth`), `shaders/base.glsl` (the BASE material — the surface every biome of the region fades into at its edge; write only the region's ground, no neighbor logic), and `region.tsx`:
   ```tsx
   export const NameRegion = () => (
     <Region spec={NAME_REGION} biomes={{ some: SomeBiome }}>
       <Material shader={baseShader} textures={{ namebasetexture: "ground.png" }} />
       <Skybox topColor=… horizonColor=… bottomColor=… />
     </Region>
   );
   ```
   Its biomes live in `regions/<name>/biomes/` (see New Biome); `<Region>` renders the `biomes` map in `spec.biomes` order (one entry per biome name, dev-asserted).
2. Append its spec to `OVERWORLD_REGIONS` (`overworld/regions/index.ts` — config.ts and the CRT's address pages read it) and add `name: NameRegion` to the `<Regions components>` map in `overworld/domain.tsx`. Adding a region MOVES existing places — the region roll is `floor(u × count)` over the region list, so every cell re-rolls: a deliberate, world-breaking change; do it before anyone has linked to an address, or accept it knowingly.
3. Optional: a noun theme in `address.ts` (`REGION_NOUNS.<name>`, 16 lowercase words unique across every list — asserted at load; append-only). `/<name>` resolves to the instance nearest the origin and gets its CRT page automatically. Nothing else: the sky mix, the height/material cross-fades, rivers and the server config all derive from the spec.


### New Domain (a genuinely separate page — today only `home` qualifies)

1. Create `src/world/domains/<name>/domain.tsx` — a `<Domain>` tree with a domain-level `<Terrain>`, `<Skybox>`, etc. and `<Regions specs={NAME_REGIONS} components={…}>` (the regions live in `src/world/domains/<name>/regions/`, their ordered list in `regions/index.ts`)
2. Add its id to `DOMAIN_IDS` (`src/net/protocol.ts` — the one definition; `DomainId` derives from it), teach `navigation.ts` how its path is recognized (today: "/" = home, everything else = an overworld address), and mount it from `src/index.tsx`
3. If the server should simulate NPCs in it: add `config.ts` (see the overworld's — `buildDomainConfigFromSpecs({ params, regions: NAME_REGIONS })`) and list it in `world/domains/configs.ts`. Today the server's physics world is initialized with ONE domain (`PHYSICS_DOMAIN` in `physicsWorld.ts`)

### New Biome

1. Create the biome folder: `src/world/domains/<domain>/regions/<region>/biomes/<name>/`. If another region needs the same biome, duplicate the folder there under a distinct component name (e.g. `CityGrassBiome` vs `GrassBiome`) with the SAME biome `id` — there is deliberately no shared biomes folder. Its id lives only in its spec (`world/constants.ts` holds just the ids the shared pipeline branches on — add one there only if a worker must branch on the biome)
2. Create `shaders/fragment.glsl` — `void main()` writing `gl_FragColor` (the assembler renames it `<name>_frag()` and strips the uniform/varying lines). Write ONLY the biome's own surface: no boundary band, no neighbor logic — the terrain material cross-fades it into whatever is next door (the max is 8 biomes per domain, two vec4 slots). Uniform names and file-scope helper names are GLOBAL across every biome/region shader: a uniform name reused for a different texture, or a helper defined twice, throws in dev naming both owners
3. Create `spec.ts` — the biome as DATA (`BiomeSpec`: unique id, unique lowercase name, joinable, optional `blendWidth`/`heightBlendWidth` — leave them unset to inherit the region/domain widths; set `blendWidth: 2` for a hard edge like the city's, keep any width under half a biome cell (250u) or presence never reaches 1; `noise` (its ONLY height definition) or `water: { depth }` for a lake; optional `prohibitRoads: true` to keep inter-city freeways off the biome's walls — the lake sets it; optional `actors`: `[{ actor: SOME_SPEC, biomeIds: [id], …overrides }]`), Three-free so the server's domain config reads it — then `biome.tsx` (see the desert dust biome for the minimal template, the city for dressing, the grass for foliage + actors):
   ```tsx
   export const NAME_BIOME: BiomeSpec = { id: N, name: "name", joinable: true, noise: { params: {...} } };
   export const NameBiome = () => (
     <Biome spec={NAME_BIOME}>
       <Material shader={fragmentShader} textures={{ nametexture: "name.png" }} />
       {/* <Dressing>…</Dressing>, <Foliage>…</Foliage>, <Skybox … /> as needed */}
     </Biome>
   );
   ```
   `<Biome spec>` registers the spec's `noise` and `actors` itself — the shared pipeline (`utils/workers/vertexCompute.ts`) evaluates the noise on workers and main thread alike, so there is nothing to keep in sync. A biome needing bespoke height code (like the city) omits `noise` and adds a branch to the pipeline instead (`zoneBiomeHeight` in `vertexCompute.ts`, its own module beside it like `roads/cityTerrain.ts`). Optionally give the biome its own RIVERBED: `<Material … riverbed={{ texture: "dirt.png", saturation: 0.3, tint: [0.9, 0.93, 1] }} />` (a module-level constant; biomes of one region sharing a bed put it in the region folder, like `regions/snow/riverbed.ts`) — the terrain cross-fades it by the biome weights under every river there; unset = the domain's `<Material riverTexture>`
4. Add its spec to the region's `spec.ts` `biomes` list and `name: NameBiome` to the region's `<Region biomes>` map — the list is the order (the render order AND what the server's config reads); a missing or extra map entry throws in dev.

The combined fragment shader branch, voronoi biome lookup, worker noise config and flatten pads are all derived from the specs — no core files to touch.

Note on duplicated biomes: registrations (materials, actors) for the same biome `id` are merged into one biome data object at commit (two different names on one id throw in dev), so a duplicate must RE-EXPORT the original's spec (`export { GRASS_BIOME } from "…/grass/spec"`) and import its shader rather than copy them; only `biome.tsx` (the component + its client-only children) is genuinely per-folder. *Visual* children (e.g. `GrassField`) are NOT merged — if two regions with the same duplicated biome are mounted at once, each duplicate renders its own grass; be mindful of that cost when mounting multiple regions that duplicate a biome.

### New Region

See "New Region (the normal way to add a 'world')" above — regions are the top of the in-map hierarchy now (no dimension level).


### New Actor (per-object spawns: NPCs, buildings, interactables)

Pick the class first: unique geometry, interaction, or behavior → ACTOR (below); many + identical + stateless → DRESSING (next section).

**Static actors** (no custom behavior — just a model at a position):
1. Create `src/objects/actors/<name>/spec.ts` exporting an `ActorSpec` (`id`, `model` GLTF path, `scale`, optionally `wholeTrimesh`/`excludeColliderNames`, and the spawn knobs `footprint`/`density`/`clustering`/`renderDistance`/`priority` — no component file, no catalog line: the server has nothing to simulate, so it defaults to `serverSynced: false`) — spawn restrictions (`heightRange`, `slopeRange`, `roadDistanceRange` — distance to the road centerline, city roads/sidewalks — `density`, spacing) are attributes inherited from the shared base (`objects/types.ts`); an actor's BIOMES are not an attribute: it spawns ONLY in the biomes whose spec lists it (its `biomeIds` = those biomes, derived at registration; `ActorSpec`/`ActorMount` cannot name `biomeIds`), and a kind for several biomes is listed in each (their union — `mergeActorListings`, `actors/spec.ts`); `quantization` overrides the global vertex-quantization grid size for this object (unset = global); `colliderDistance` defaults to min(500, renderDistance/2). Actors live outside biome folders because one actor may be placed in several biomes. Variants extend a base by SPREADING its spec (`SKYSCRAPER_SPEC = { ...BUILDING_SPEC, … }`).
2. Place it: `{ actor: NAME_SPEC, …overrides }` in the `actors` of every biome it spawns in (registered by `<Biome>`; a biome's `actors` is everything that spawns there)
3. Place GLTF model in `public/models/`

**Foliage** (mass vegetation — thousands of instances per chunk, its own class):

*To USE an existing plant:* mount `<GrassField>` (`src/objects/foliage/grass/GrassField.tsx`) inside the biome's `<Foliage>` group — it auto-restricts to the enclosing biome via `BiomeContext` (pass `biomeIds` explicitly to override). Every knob is an override at the mount: filters (`density`, `heightRange`, `slopeRange`/`slopeBlend`) and visuals (`color`, `png` or a procedural `texture`, `width`/`height`, `sway`/`swaySpeed`, `renderDistance`, `seed`, `quantization`); precedence is mount > `<Foliage>` group > plant defaults, as for `<Dressing>`. Placement runs in `foliage.worker.ts`; rendering is one instanced, camera-facing, GPU-swaying draw call per 64-unit chunk.

*To ADD a plant type* (shrub, fern, wheat) — there is NO pipeline to write, the base (`src/objects/foliage/Foliage.tsx`) is the whole thing:
1. Create `src/objects/foliage/<name>/<Name>Field.tsx` — copy `grass/GrassField.tsx` (~60 lines): draw or load the billboard art, then `export const XField = createFoliage({ … })` with this plant's defaults.
2. Give it its OWN `seed`. Two plant types sharing a seed at the same density place on identical points and grow through each other (dev console.errors when two plant types are mounted on one seed).

**Procedural buildings** (seeded shape, real nested interiors, clickable doors — no GLTF):
1. `src/objects/actors/building/` — `<Building>` generates a deterministic building from a seed (default: spawn coordinates), interior-first: rooms-per-floor × floors set the interior area, which sets the exterior footprint and height (so the shell realistically wraps the inside). Exterior: 4–8-sided masses — boxy slabs or rotated faceted canisters — grayscale segments with occasional accent colors, lips/bulges, gentle lean, scattered oval/skewed-quad windows, rooftop caps + crooked pipes; colors baked as vertex colors so all buildings share one material. Night window lights: each building has `windowLightChance` (0–1 fraction of windows that light per night; default 0.6, 0 = never) and `windowLightIntensity` (emissive strength of lit glass, default 1.4) — a shader patch on the shared exterior material (per-vertex vec3 `aWindow` = stable per-window random + chance + intensity, global uniforms driven by `getWindowLightsProgress()` and `getNightIndex()`) hashes each window against the per-night seed, so a DIFFERENT subset pops on sporadically over LIGHTS_TRANSITION_DURATION_MS each nightfall (off at dawn the same way), washing the glass yellowish with an emissive glow. No extra draw calls or light objects.
2. Exterior and interior are ONE building (the interior MESH is built on the first close approach, see 3): the shell has REAL THICKNESS — the outer surface leans/tapers/bulges freely, while the INNER surface is a straight PRISM of the interior polygon through the occupied floors (the wall cavity between them varies in thickness). A constant inner surface means BSP split walls extend EXACTLY to it at every story: a two-room floor is one dividing wall running exterior-to-exterior, never an enclosed room-within-a-room (wall ends on the BSP domain boundary are stretched to the polygon via `ringSpanAt`, tucked into the cavity). Ramps: EACH story gap gets its own independently placed straight-run ramp (random spot + axis/direction per gap, so floor 1→2 differs from 2→3), sitting OPEN inside a normal room — stories generate in order, placing the gap's shaft first (clear of the arrival hole/landing from below; clear of exterior door zones on the ground floor), then BSP-ing the floor around it: split walls, pillars, doorways, light panels, and child slots all avoid the shaft footprint and the arrival rects, and a split wall never T-junctions into a perpendicular wall at its doorway. Door openings get jamb reveals closing the cavity, and doors auto-nudge along their edge away from wall ends that dead-end into the perimeter. The interior renders as a single merged vertex-colored UNLIT mesh (walls, polygon slabs with per-gap ramp holes, ramps, light panels) with a fixed wrap-lambert BAKED into the vertex colors at build time (light panels excluded, staying full-bright) so same-color surfaces still read as separate planes at zero runtime cost; interior colors derive from the exterior ground-segment color (floor darker, ceiling lighter) and are overridable via the `interiorColors` option. The plan generator clamps outer-shell rings through the occupied floors (apothem-corrected for polygons, including an inserted ring exactly at `interiorTop`) so the shell never cuts inward — shape runs free above the top floor. The shell carve, inner carve, and door leaf share the same ring edge + param.
3. Door mechanic: each opening holds a real hinged door leaf (closed = extra cuboid collider). Clicking it (screen-center raycast ≤ `DOOR_INTERACT_REACH` 6u, cursor grows on hover) swings it open locally as a prediction and sends `door:<i>`; the server toggles the replicated state for every registrant after checking the player is within 6 + 3u of THAT DOOR (its position in the same seeded plan the sealed hull comes from — `doorOffsetsFor`, `server/src/game/physics/buildings.ts`). INTERIOR LIFECYCLE (Building.tsx): the first time the player comes within `INTERIOR_DISTANCE` (60u) the interior MESH is built (one queued task, `ensureBuildingInterior` — the main build only makes the interior COLLIDER data, `buildInteriorParts(plan, "colliders")`) and mounted together with the building's `children`; from then on it stays mounted with whatever state its children hold until the building DESPAWNS (the refcounted cache disposes it when the last mount releases) — walking away only hides it (beyond `LIVE_DISTANCE` 150u, where the matrices also freeze). This is deliberate groundwork for items/NPCs inside: enter, change things, leave, come back, and it is as you left it unless you walked far enough to despawn the building. Interior state never depends on colliders (still <120u real, hull beyond). (This replaced the old render-to-texture portal system, which has since been REMOVED from the codebase entirely.)
4. **COLLIDER LOD — a building is NEVER without a collider** (`proxyCollider.ts`); only the fidelity changes with distance. **detail** (<120u): the real colliders — shell trimesh, interior walls, slabs, ramps, closed door leaves; doors work, mounted as React children under `<RigidBody>`. **hull** (beyond): ONE convex hull over the shell's 2D SILHOUETTE extruded bottom-to-top (`buildProxyHullVertices`, cached per seed on the assets), which TRACKS THE FOOTPRINT so an NPC contacting it reads as touching the wall. There is no third tier and no distance gate of its own: the proxy exists exactly when `!collidersActive`, so the collider gate's hysteresis covers the only swap there is. Why NPCs need any of this: they live out to ~243u and used to walk straight through distant walls, and the real colliders can't be everywhere (two trimesh QBVH builds, several ms each, hence the base's one-building-per-50ms activation throttle). Rapier QuickHulls whatever it is handed on every mount, so the input is kept MINIMAL: the silhouette is computed here (Andrew's monotone chain, deterministic — every client must agree on a cached-per-seed hull) and Rapier gets ~14 points where every ring corner of every level was ~83, worst 133, measured over 40 seeds. The prism is deliberately slightly FATTER than a hull over the raw corners — where the shell tapers or leans it keeps the full silhouette at every height — so it still contains the shell everywhere, seals at least as well, and costs fewer faces. Roof caps and pipes are deliberately excluded — nothing walks on them and letting them widen the hull would block NPCs further out in the street. A single enclosing AABB CUBOID was tried INSTEAD of the hull and REMOVED: cheapest possible shape (nothing to construct), but a 45°-rotated square's AABB is ~1.41× its width, so NPCs stopped short of facades and big rotated buildings blocked the sidewalk. NON-DEGENERACY IS AN INVARIANT, not a nicety: a degenerate cloud makes `ColliderDesc.convexHull` return null and, with the hull as the only proxy shape, that building would be passable — the desc is therefore built BEFORE the rigid body so a null can't leave an empty body behind, and `proxyCollider.test.ts` asserts it (plus determinism, the point count, and the covering guarantee against every loft's ring corners within the hull's height band). The proxy is built IMPERATIVELY (`world.createRigidBody` + `ColliderDesc.convexHull`, via `createProxyCollider`), NOT as `<RigidBody>`/`<ConvexHullCollider>`: hundreds of extra Object3Ds would pay `compose()` per frame — the exact cost the actor's matrix freezing exists to avoid — and a React collider under a frozen (`matrixWorldAutoUpdate = false`) group has no current world matrix to read. The handle is solid from creation, so there is no frame between assets landing and the first distance check in which a building is passable. Being convex it has NO door, so it SEALS the building — right at range, and why it is swapped for the real colliders up close. Whatever is INSIDE when a sealed tier appears simply STOPS MOVING, and that is DELIBERATE — not a bug to fix: a character controller embedded in a convex shape has a blocking contact in every direction, so `computeColliderMovement` hands back `computedMovement()` ≈ 0 and the body writes the position it already had, while the mixer — driven by the state machine, which never touches physics — keeps the walk cycle playing on the spot (a beeble's idle short-circuit then skips the shape cast entirely once its machine settles). A beeble jogging in place inside a distant building is the system working. An explicit freeze system (`setFrozen` on the state machine + a paused mixer + a Rapier point query for "am I inside a hull") was built for this and REMOVED as redundant — containment already freezes position, which is the whole requirement. The one input that is NOT self-limiting is GRAVITY: if `computedGrounded()` reads false while embedded, the beeble's vertical velocity integrates with no terminal clamp (it has no equivalent of the player's near-ground fall clamp, and no analytic backstop to catch it), and a large downward sweep starting inside a shape is exactly the tunneling case — if an occupant ever drops out the bottom of a sealed building, clamp that first. PERFORMANCE, and what is actually KNOWN vs assumed: the proxy colliders own NO React state — the tier is driven from the base's `onFrame` through the handle, because a `setState` from the frame loop re-renders that Building and defeats `ActorPool`'s element-identity bailout (it hands back cached elements so unchanged buildings never reconcile), MEASURED as a 1–5 fps LOSS on its own, worse than the work it was gating. Two large reductions in hull work were then measured as NO change at all — an 85% cut in the number of live proxies (a 320u band, since removed) and a 6× cheaper point cloud (~14 points vs ~83, worst 133, over 40 seeds) — so the hull count is NOT a known cost and nothing here should be assumed to be one. Eliminated by reading the code, in case it comes up again: `<Physics>`'s per-frame sync only walks R3F-registered bodies and `forEachActiveRigidBody` (fixed bodies are never active); the rapier context memo (`[paused, step, debug, colliders, gravity]`) is stable in steady state, so `useRapier()` in every Building does not churn renders. The FLIP SIDE of that first fact is a hard invariant: r-t-r's frame loop runs `rigidBodyStates.forEach` over EVERY MOUNTED `<RigidBody>` COMPONENT every frame (`getRigidBody` + `isSleeping` wasm calls per body at minimum, a full translation/rotation → compose/decompose → lerp/slerp path for non-sleeping ones), so the mounted-component count must stay a handful. A "build once, keep the detail `<RigidBody>` mounted but disabled, prebuild inside a 220u ring" variant of the collider LOD was BUILT and REVERTED as a measured fps regression: it multiplied mounted bodies ~10-20× (plus a several-seconds one-build-per-50ms burst on entering the city). If build-once/reuse is ever wanted again it must be IMPERATIVE like the proxy (bodies rapier-side only, never React-registered), with only the doors' RigidBody left in React inside the gate. A devmode checkbox that flipped every proxy collider in the world in one frame existed for exactly this measurement and was REMOVED once the answer was in — proxies are always on. Note `physics debug` rebuilds line geometry for EVERY collider in the world each frame, so it is not a valid baseline for this.

## Coordinate Precision (distance from the world origin)

The world is unbounded, so **the split between float64 and float32 is an architectural invariant, not a detail**.

- **Generation is float64 and stays ABSOLUTE.** The height pipeline (`vertexCompute.ts` and its modules), the voronoi/city/flatten engines, and every `seedRand("…x,z…")` run in JS doubles on absolute world coordinates. Measured: pipeline cost is flat from the origin out to 5×10⁷ (the seeded-RNG cost does not grow with the coordinate string either), and the circumcenter math holds to ~10⁻⁵ units at 10⁷. **Never rebase generation** — it is the one thing that must not move, or every seed changes and the world is not the same world.
- **Rendering is float32 and must never form an ABSOLUTE world coordinate.** GLSL resolves ~0.008u at 100k units from the origin and ~0.06u at 1M. That is a THIRD of the 0.025u quantization grid (`PostProcessing` sets it globally), so quantizing absolute positions made vertices flip lattice cells every frame — geometry visibly swimming, worse the further out you go — and past ~420k units `worldPos / 0.025` leaves float32's exact-integer range and collapses into stretched garbage triangles (a fill-rate cost, not just a visual one). It also stair-stepped world-space texture UVs and broke the city shader's `fwidth()` seam guards, which measure a varying's gradient against `vWorldPosWrapped`'s.

  So every vertex shader builds world position as **(rebase origin) + (offset from it)**, never as one absolute number, and projects through a view-space origin the CPU already resolved in float64:

  - `mat3(modelMatrix) * position` drops the translation → an offset that stays object/chunk-sized and exact anywhere in the world.
  - `modelViewMatrix[3].xyz` is the object origin in VIEW space, computed by three.js on the CPU in doubles; `viewPos = modelViewMatrix[3].xyz + mat3(viewMatrix) * localOffset` is exactly `modelViewMatrix * position`, without the float32 world round-trip. This is what `projectionMatrix * viewMatrix * worldPos` was throwing away.
  - **Terrain** (`world/shaders/vertex.glsl`) additionally WRAPS the chunk origin to `WORLD_WRAP` (4200) so `vWorldPosWrapped`/`vWorldUv` stay small for texturing and `fwidth()`. Consumers that compare against ABSOLUTE CPU-side positions — the lamp-glow grid lookup and the terrain's point-light loop — must use `vWorldPosAbs` (the unwrapped position, also exported by the vertex shader) instead: comparing them against the wrapped `vWorldPosWrapped` aliased lighting onto the wrong chunks (lit/unlit tiles per wrap cell). `vWorldPosAbs` carries float32 absolute error (~0.06u at 1M) — fine for smooth lighting falloffs, NEVER for tiling/quantization/`fwidth()`. 4200 is a common multiple of every world-space period downstream — the 26.25u texture tile (×160), the 75u sidewalk tile (×56), the 200u fbm cell (×21) — and of both quantization grids (0.025 ×168000, 0.2 ×21000), so the wrap is invisible: `fract()`/tiling land on identical values and the quantization lattice keeps its world phase. Chunk centers are always multiples of 210, which makes the `mod()` exact. **Anything new that reads `vWorldPosWrapped` with a world-space period must divide 4200**, or it seams every 4200 units — which is why `fbm` became `worldFbm(worldXZ, scale, octaves)` with a matching repeat period (`common.glsl`); feeding it raw absolute coordinates also pushed `hash()`'s `sin()` past what float32 can resolve, degenerating the noise into banding.
  - **Quantization** (`vfx/quantization.ts`) snaps the object-relative offset with `qPhase = mod(modelMatrix[3].xyz, uGridSize)` re-anchoring the lattice to the world, so the wobble doesn't slide with the object. `qPhase` inherits the float32 model matrix's error but is CONSTANT per object — a fixed sub-cell offset, not flicker. The `USE_INSTANCING` branch keeps the old absolute math (`modelMatrix * instanceMatrix` is still the correct absolute position under the dressing rebase below — quantizing it would just reintroduce float32 absolute precision); no instanced material is quantized today.
  - **Dressing instancing** (`finalizeInstancedChunk` in `objects/dressing/Dressing.tsx`) — every instanced chunk (markers, lamps, signals, poles, wires) is REBASED: instance matrices are composed with absolute float64 placement, then the mesh is parked at the extents center and the stored translations made relative to it, so the chunk→camera translation resolves on the CPU in float64 (`modelViewMatrix`) and the GPU only sees chunk-sized numbers. Meshes at the world origin with absolute instance translations visibly JITTERED past ~100k units. The explicit culling sphere is LOCAL to the mesh (three applies matrixWorld). All four features flow through this one function — keep it that way.
  - **Skinned actors** (`RootRelativeSkeleton` in `objects/actors/modelClonePool.ts`) — three's stock skinning writes ABSOLUTE `bone.matrixWorld × boneInverse` into the float32 bone texture and cancels it against `bindMatrixInverse` per-vertex on the GPU, so beebles jittered far from the origin. The clone pipeline instead stores ROOT-RELATIVE bone matrices (`rootWorld⁻¹ × boneWorld × boneInverse`, cancelled in float64 on the CPU) and freezes each skinned mesh's `bindMatrixInverse` at its constant root-relative value (mesh nodes never move relative to the model root; the per-frame attached-mode sync is overridden away). Mathematically identical for the GPU path. The CPU path must be kept in step BY HAND: three's `applyBoneTransform` reads the absolute `bone.matrixWorld` itself (it never touches the skeleton's bone matrices), so the frozen bind alone made it return near-WORLD-space points, which `computeBoundingSphere`/`computeBoundingBox`/`raycast` then re-multiplied by `matrixWorld` — a culling sphere at twice the actor's world position, so beebles VANISHED once that constant offset subtended more than the FOV (i.e. as the player approached). It is overridden per skinned mesh (`applyBoneTransformRootRelative`, using the skeleton's cached `rootInverse`), and each mesh's `boundingBox`/`boundingSphere` are FROZEN at creation in rest pose at the origin (padded by `SKINNED_BOUNDS_PAD`) — three would otherwise compute them lazily at the first frustum test, out at the spawn coordinates, and cache that for the clone's whole life including pool reuse.
  - **Foliage** (`objects/foliage/Foliage.tsx`) keeps its `offset` attribute absolute but puts the chunk mesh AT its chunk origin and works from `offset - modelMatrix[3].xyz` (exact — an instance is never more than one chunk away). Chunk size 32 is a whole multiple of both grids, so the relative lattice IS the world lattice. Camera-relative and wind terms deliberately keep using the absolute offset: they are differences or low-frequency phases, and the wind must stay continuous across chunk borders.
- **Physics is float32 too** (Rapier), and this is NOT addressed: collider/contact resolution degrades at the same rate (~8mm at 100k, ~6cm at 1M) — so a MOVING kinematic body (beeble, player) at extreme distances still carries Rapier-level position noise even though its rendering is now precision-clean; idle/static objects are fully stable. Fixing it means a real scene-graph floating origin — rebasing bodies, camera, and every `camera.position` consumer — while generation keeps its absolute coordinates behind a `+ worldOrigin` conversion.

## Performance Notes

- **Physics steps ONCE PER FRAME** (`<Physics timeStep="vary">` in `world/CustomCanvas.tsx`): every kinematic body is driven per frame from `translation()`, and r-t-r's default fixed 1/60 accumulator made them move at 60/fps of their speed above 60fps (~40–60% at this project's 96–145fps; the LAST `setNextKinematicTranslation` before a step wins). Invisible until the server walked NPCs at true speed — the client body then lagged, slid on after every stop, and snapped forward to catch up (found Sept 2026, after Phase 3 of the server physics work). CONSEQUENCE: the player's speeds/gravity/jump were tuned UNDER that bug, so they now act at their true values at any framerate — retune `WALK_SPEED`/`SPRINT_SPEED` (Player.tsx) and `GRAVITY`/`JUMP_IMPULSE` (physics/characterMovement.ts — shared with the server) if the feel is off. Never go back to a fixed step without driving kinematic bodies from the fixed step.
- **Canvas/physics settings are deliberate** (`world/CustomCanvas.tsx`): `dpr` capped at 1.5 (`MAX_DPR`), `antialias: false`, `alpha: false` — R3F's defaults (dpr 2 + MSAA + alpha) quadrupled the fragment budget of the full-screen terrain shader for a quantized low-poly look. `<Physics interpolate={false}>`: the scene has no dynamic bodies, and r-t-r's interpolation snapshot walked EVERY body (500+ in the city) before every step.
- **Terrain LOD range is bounded by the camera far plane** (`lodConfig.ts`: LOD4 6720u, LOD5 8400u vs `CAMERA_FAR` 7200, `player/constants.ts`) — chunks past the far plane were generated, pooled and kept without ever producing a pixel. `releaseGeometry` nulls the bounding sphere/box: a pooled geometry otherwise kept the FIRST chunk's cached sphere.
- **Far visual-only terrain LODs skip the freeway RUNS** (`computeVertexDataFar`, the terrain worker's `visualOnly = !lod.hasCollider`, the same flag that skips pads): LOD3–5 vertices are 210–3360u apart and cannot resolve a 14u road, and routing the runs (`getNetwork`) for their cells was ~half of the startup ring's worker time. The belt, the city and everything else stay exact (the rivers too, except at LOD4–5 — next bullet); collider LODs, the server, the main thread (`vertexData.ts`), spawn/foliage/dressing workers never take this path, so physics matches. MEASURED around a city spawn (228 chunks, one process, 3 runs): LOD3 886–948 → 114–126 ms, LOD4 1570–1805 → 582–682 ms. The visible cost is the aliasing a far vertex used to pick up when it happened to land within ~24u of a run: its height moved onto the road grade (max 9.9u, median 0.36u over the 314 affected vertices at 77 run × LOD3-edge crossings in a 24 km square) and a smear of asphalt paint; both are gone past LOD2. SEAMS: the worst LOD2|LOD3 gap at those 77 crossings is unchanged (LOD2 edge ≤ 37.8u above the LOD3 segment vs its 80u skirt, LOD3 ≤ 36.4u above LOD2 vs 160u) — a run-graded vertex on the LOD2 side is always inside the finer chunk's skirt. (Along four map-spanning lines the pre-existing LOD2→3 gap reaches 78.8u of the 80u skirt — unrelated to roads, and close to the limit.)
- **LOD4–5 skip the RIVER FIELD too** (`LODLevel.carvesRivers` → the worker message field → `computeVertexDataFar(x, z, false)`, which sets `noRiverSample()`/`noRiverQuay()` instead of evaluating `riverFieldAt`/`riverQuayAt`): no channel, no river water, bed paint distance Infinity (the shader's own "no river" value, the same one every vertex out of a river's reach ships), no city quay — the un-carved terrain; lakes are untouched. At 840u/3360u spacing a river drew 0.1–0.5% of its true water area as isolated specks, while building the per-cell river lists (each evaluates the terrain at every piece end) was ~90% of those chunks' build time. MEASURED, startup ring at 3 spawns (fresh process each, 2 runs): LOD4 369–548 → 36–50 ms, LOD5 51–118 → 2–5 ms, the whole ring −20% / −31% / −31% (2648 → 2114, 1435 → 984, 1653 → 1143 ms). ~5% of their unique vertices change (trenches up to 47.6u filled). LOD3 was measured and KEPT carving: skipping it too saves a further 60–110 ms (ring −22/−37/−37%), but at 210u spacing it still draws 3–22% of a ring's true river water (a wide river near the ocean reads as a dotted strip) and would end every river at the 1680u LOD2 ring. SEAMS (every chunk edge line over a 48 km square): LOD3|LOD4 LOD3 above LOD4 ≤ 144.3u (skirt 160), LOD4 above LOD3 ≤ 130.3u (skirt 260) — the worst at a carved LOD3 river vertex is 88.8u under the dry LOD4 segment, which the LOD4 skirt covers; LOD4|LOD5 unchanged (146.8u / 136.3u vs 260 / 400). The same scan found a PRE-EXISTING LOD2|LOD3 gap unrelated to rivers: on a mountain (−8295, 10080) the LOD2 edge stands 115.8u above the LOD3 segment, past LOD2's 100u skirt.
- **The freeway network is LAZY per context** (`networkOf(ctx)` in `roads/freewayNetwork.ts`, memoized on grid identity): building every context's cell network (~5–20 ms) in `getBiomeContext` cost every caller, and most never read it — the river surfaces (`riverSurfaceAt` samples a context per river point), `getPlaceInfo` (sky + address bar polls: 676 probes 4470 → 174 ms, the seedRand port included), zone lookups. Exact (every output identical), −12% on the startup ring.
- **`seedRand` is an exact port of seedrandom's ARC4** on two reused byte arrays (`utils/math/_math.ts`, compared bit-for-bit against the library in `_math.test.ts`): ~2.3× faster per call (4.3 → 1.9 µs, MEASURED in node) — the library allocated a generator, closures and two 256-entry arrays per call and mixed each state into its global entropy pool. It was the pipeline's largest self time (~20% of the startup ring): ring −13% (the LOD1/LOD2 chunks of a NEW area −13–17%, where flatten tiles and sites are rolled; a warm LOD1 grid is unchanged). Never change the port's arithmetic: every seed ever rolled (addresses, sites, spawns) is its output.
- **Scene point lights follow the night blend** (`CityLights` writes `intensity × nightBlend` per frame) and the terrain shader's point-light loop is gated on `uNightBlend > 0.001` — by day six lights were shaded on every lit and terrain fragment for nothing.
- **Far building doors are ONE instanced draw** (`building/farDoors.ts`): a lit draw call per door out to 625u was hundreds of draws for a few pixels, so doors used to vanish past 220u. Now the real leaves draw only inside `LIVE_DISTANCE` (150u) and every other door in the world is an instance of one InstancedMesh.
- **The grass fragment shader samples each texture layer only where its weight is visible** and uses 1 fbm octave for the slope-threshold nudge (3 octaves = 12 `sin()` per fragment for a ±0.05 offset).

- **Terrain build loop is TIME-budgeted** (`BUILD_BUDGET_MS` in `TerrainRenderer.tsx`, ~5ms, ≥1 chunk per pass) and the whole update pass EARLY-OUTS in steady state: the desired chunk set is recomputed only after ~8u of camera movement, and once queues are drained and the last built chunk is visible the per-frame pass is a single flag check. Chunk keys are cached on the `Chunk` object — never rebuild them from float math in a loop.
- **Terrain finishing runs in the worker**: the local vertex grid (pure function of chunkSize/segments), the vertex normals (main-grid triangles only — skirt normals are edge copies), and the Rapier column-major collider heights are all computed in `terrain.worker.ts`; the main thread only writes buffers.
- The voronoi lookups (`utils/workers/voronoi.ts`) use O(n) nearest-entry scans instead of sorting. Grid arrays are never mutated by lookups. Every per-vertex wall pass is ONE loop over the local wall list (`accumulateWallFields`) filling preallocated scratch arrays — no per-vertex allocation.
- Delaunay triangulations AND wall lists are cached via `WeakMap` keyed by grid array identity (`delaunayCache`/`zoneWallsCache` in `voronoi.ts`, `wallsCache` in `vertexCompute.ts`).
- Cache eviction in the worker only runs on cache misses, not every query. Hot Maps (`flattenTileCache`, `flattenCandCache`, city cell/scalar caches) evict the OLDEST HALF on overflow (insertion order ≈ proximity) — never `clear()`: a flatten tile costs 30–70ms to rebuild and a full clear floods the next queries.
- `getDistanceToWall` uses inline segment-distance math (no THREE object allocations).
- `buildChunk` reads position buffers directly as Float32Array (no Vector3 per vertex).
- **LOD ring tuning** (`lodConfig.ts`): LOD1 (96 seg, 4.375u spacing) covers only the innermost 420u ring — it previously reached 840u and carried 92% of ALL terrain triangles. LOD2 runs 24 segments (17.5u) to soften the density cliff. The player always stands on LOD1, so the measured slope-slide tuning is unaffected.
- **Skirt depth is PER LOD** (`skirtDepth` on each `LODLevel`: 30/230/460/1000/450 (re-measured after the mountain domes)): the finer chunk's skirt must exceed the worst height its coarser neighbor's straight segment misses by, and that grows with vertex spacing — measured along four map-spanning lines of the overworld: 3u, 55u, 113u, 175u for LOD1→2…LOD4→5. The previous single 30u skirt covered only the LOD1→2 boundary; the desert region's own base noise (1800u wavelength vs LOD4's 840u vertex spacing) is what drives the coarse numbers up. (A report of "open seams at chunk edges" prompted this; it may have been a dev-server restart mid-load rather than these gaps, but the gaps are real and measured, and deep skirts on far chunks cost nothing.)
- **ALL actor per-frame work runs through ONE shared driver** (`driveActorFrames` in `actors/Actor.tsx`, subscribed by ActorPool's useFrame): every actor — GLTF or procedural, buildings included — registers a latest-closure ref via `useActorLifecycle` instead of its own `useFrame`, so hundreds of mounted actors cost one R3F subscriber (no subscription churn per spawn batch) and the shared frustum is computed exactly once per frame. The loop uses ONE 2D squared distance for everything (fade, kill, proximity, collider gate, near gate, animation LOD) and never allocates. Do NOT add a `useFrame` to an actor — pass `onFrame` to the lifecycle.
- **Animation LOD** (`actors/ModelActor.tsx`): mixers don't update while frustum-culled and run at half rate past 40% of render distance; skipped time accumulates (capped) so loops stay continuous. NOTE: this skips interpolant evaluation only — the renderer still runs `skeleton.update()` + a bone-texture upload for every VISIBLE skinned mesh; only frustum culling removes skinning cost.
- **GLTF clones are POOLED per (model | quantization)** (`objects/actors/modelClonePool.ts`): despawn/respawn churn used to re-run the full clone pipeline per mount (scene clone, traversals, material clones + shader patches, skeleton rebind, bbox measure) and dispose it all again on unmount — a reused clone now costs a map lookup + opacity reset. Bounded per key; only evictions dispose (materials + skeleton bone textures; geometry is SHARED with the source GLTF, never disposed). Release is deferred one macrotask and cancellable so React 18 StrictMode dev remounts can't hand a still-mounted scene to another component. Pools survive domain switches (clones are domain-agnostic; no-override materials follow the live global quantization uniform — override values are baked, hence part of the key).
- **Skeletons are shared across a clone's meshes** (`cloneModelWithAnimations` in `modelClonePool.ts`): all skinned meshes bound to one source skeleton share ONE cloned skeleton (beeble: 10 meshes, 1 skeleton) — a skeleton per mesh multiplied skinning + bone-texture uploads 10×. Bones indexed by name in one pass; materials deduped per source material; clip actions bind LAZILY on first command (beeble ships 10 junk clips) and persist on the pooled record.
- **Actor behavior runs in ONE onFrame** (`ModelActor.tsx`): the state machine tick, the mouse raycast (every 3rd frame, phase-offset), the mover step and the animation apply all run inside the actor base's single frame callback — the beeble used to own three `useFrame`s (physics + one inside each of useStateMachine/useMouseEvents), each recomputing the camera distance the actor base already had. (A synced actor's client machine only mirrors; the server does the physics.)
- **Beeble "ascend" morph restores the pooled clone** (`stateMachine.ts`): the state swaps private cloned geometries onto the mesh nodes and its onEnter cleanup puts the shared GLTF geometry back + disposes the clones; without it every ascended beeble leaked its buffers and handed a sphere-morphed body to the next beeble reusing that pooled clone.
- **The collider worker moves typed arrays with transfer lists** both ways (`objects/actors/colliders`): positions/indices are private `Float32Array`/`Uint32Array` copies of the GLTF buffers (never the live ones — transferring those would detach them from the renderer), and `TrimeshCollider` passes the result straight to Rapier.
- **Never attach R3F pointer handlers to spawned actors** — even no-ops register the object in R3F's interaction list, which raycasts it RECURSIVELY (CPU-skinned triangle tests included) on every pointermove at mouse-polling rate. All actor input goes through window listeners + the manual screen-center raycast in `useMouseEvents` (which angular-pre-tests before touching triangles).
- **Throttled per-N-frame work is PHASE-OFFSET per instance** (hash of spawn coords/seed) — counters all starting at 0 made every object in a spawn batch do its "every 3rd frame" work on the SAME frames, preserving the spikes the throttle was meant to remove.
- **GPU uploads are paid at MOUNT, not at first look** (`utils/uploadOnFirstDraw.ts`): three uploads a mesh's buffers/textures AND links its shader program on its first actual DRAW, so content mounted behind the player (a spawn radius is a circle; the player faces one way) deferred all of it to the frame the player first turned toward it — a fast 180° cashed in every deferred upload at once (the turn-around lag spike). The helper forces one off-frustum draw (vertex cost only), then restores culling. Applied to terrain chunks, building meshes, grass chunks, dressing chunks, and GLTF actors (paid once per pooled clone at CREATION — modelClonePool; the actor base additionally holds `group.visible` true for 3 warm-up frames — its own frustum culling would otherwise hide the group before the forced draw could happen; those late actor compiles were the last 50-90ms render-internal spikes). Apply it to any NEW mass content that can mount off-screen.
- **Lag-spike attribution stays wired in** (`utils/spikeTrace.ts`, `window.__spikeTrace`): hot systems trace their heavy spans (`render` = the whole gl.render — a spike INSIDE it is GPU/driver work; `terrain:finish`, `building:phase*`, `building:finish`, `spawn:commit`, collider-commit markers). To hunt a spike: record rAF deltas, and on a long frame read `__spikeTrace.traceWindow(frameStart, frameEnd)` — an empty window with no heap jump means the browser/OS, not the game. Overhead is one timestamp pair per traced call; leave it on.
- **Spawn fades cost nothing once settled** (`vfx/spawnFade.ts`): an object is on twin materials only while it fades; after that it draws with its shared base materials again (batching intact) and the per-frame driver is a flag check. The shared shaders carry one uniform-coherent `discard` branch; an in-page A/B toggling it out measured no fps difference.
- **Every TaskQueue shares ONE per-frame budget** (`utils/task-queue/TaskQueue.ts`: 6ms per frame for ALL queues together, reset on requestAnimationFrame, the work itself runs in a macrotask after the frame paints; below ~30fps it grows to 20% of the frame, max 50ms, so a slow machine still streams): awaiting a synchronous task only yields a MICROtask, so without a budget a burst of queued work would run inside one frame. Four queues each budgeting ONLY ITSELF (buildings, GLTF clones, dressing, city lights) ran their slices back to back — MEASURED in a headless-Chrome harness replaying real building-phase costs, city-entry burst: queue work between frames p95 15.7ms / max 18.9 → 7.7 / 10.7 with the shared clock, frame interval p95 19.3 → 12.6ms (at 3× costs: p95 work 22 → 13ms, frame p95 27 → 18ms). PRIORITY (Sept 2026): every task carries the world position it is for (`addTask(task, { at })`) and its RANK = distance to the focus (the camera, `setWorkFocus` from ActorPool's frame) × its queue's weight + bias, re-measured at every pick; the lowest rank in ANY queue runs next, a queue picks any of its own tasks (equal ranks stay FIFO; least-used queue wins a tie), so work the player has driven past falls behind the work in front of them. Weights: buildings/GLTF clones 1, dressing 1.5, city lights biased into the background. Ranks above `BACKGROUND_RANK` (600) run only in budget nearer work left, and while the machine is struggling (frame EMA > 25ms) only in the first quarter of it. Multi-phase jobs chain (each building phase queues the next) so the NEAREST building completes first. Terrain shares the notion without joining the queue: `isMachineStruggling()` throttles far LODs to one per 250ms after load, and `chargeFrameWork(ms)` bills each chunk's main-thread finish to the same frame budget. A queue awaiting a worker never holds up the others, and a task overrunning the budget borrows from the next frame (at most one budget). A task is charged its synchronous part when called and, when it settles, the time since the later of that and the last macrotask boundary (a self-rearming zero-timeout marks boundaries while any task is suspended), so a worker round-trip is not charged as work. Cost: under a full four-queue backlog buildings drain ~35% slower (the whole burst is dressing/worker-bound and finishes in the same ~1.5s); one queue alone is as fast as before. Terrain is NOT on a TaskQueue (its own `BUILD_BUDGET_MS` in the frame loop, LOD1 → LOD2 → far, nearest-first).
- **Procedural building assets build through a TaskQueue** (`Building.tsx`): cache-hit seeds mount synchronously (despawn/respawn churn); NEW seeds render null while the build runs as FOUR queued tasks (plan → exterior → interior → assembly, `beginProceduralBuildingBuild`) — the queue's time budget only yields BETWEEN tasks, so as one monolithic task a heavy skyscraper was a single long frame no budget could split. Full off-thread (worker) geometry building was BUILT and then REVERTED by preference: it worked (three's triangulators run fine in a worker; typed arrays transferred back), but measured no fps benefit — the sliced main-thread build was already budget-bounded, so the worker only relocated hitch-class latency while adding a second three bundle, a thread, and mount-pacing complexity (the worker returned results faster than frames render, so mounts/warm-draw uploads bunched and needed re-throttling). Revisit only if `building:phase*`/`building:finish` spans show up as real hitches AND the sliced build can't be tuned.
- **Building asset cache is REFCOUNTED** (`buildingAssets.ts`): mounted buildings retain their entry; eviction only ever disposes refcount-0 entries (LRU by release time, `MAX_IDLE_CACHE`). The old fixed-size FIFO disposed geometry still attached to RENDERED meshes once mounted buildings exceeded the cap (~300–600 in the city vs 64 slots) — a correctness bug, not just perf. Slab profiles triangulate once per (thickness, holes) and are copied for floor/ceiling/collider.
- **Buildings freeze their matrix subtree when far** (`matrixAutoUpdate`/`matrixWorldAutoUpdate` off outside children range, re-enabled inside it): hundreds of static buildings were paying `compose()` per Object3D per frame. Doors/colliders/children only act inside the live zone, so alignment is guaranteed by construction. The interior mesh exists only for buildings the player came within 60u of, and is hidden beyond `LIVE_DISTANCE` (it's fully occluded beyond a few pixels of door opening) — hidden, never discarded, until the building despawns.
- **The foliage worker pre-probes chunk emptiness** (center + four corners `computeVertexData`, mirroring the dressing enumerators' `chunkMayHoldBiomes`) before sampling the 33×33 terrain grid, and the foliage base never requests chunks whose nearest point exceeds the fade-zero distance — instances past the fade are invisible but still cost full vertex work. The sampled grid is kept in a bounded LRU (`GRID_CACHE_MAX` 256, ~22KB each) so a band widening (next note) re-runs only placement, and skips the probe.
- **Foliage instance counts are distance-tiered via `instanceCount` truncation** (`LOD_TAPER_*` in `Foliage.tsx`): the worker delivers each chunk's instances SORTED by the shader's per-instance fade key (longest-lived first), so each sweep can truncate a chunk's `instanceCount` to exactly the instances its distance hasn't faded to zero — visually free — plus a mild mid-band density taper (tunable). Measured: grass was 14.6M of 14.8M rendered triangles; this halved the total (96→145 fps standing in the city). If the worker's instance ORDER ever changes, this truncation silently becomes spatially biased — keep the fade-key sort. **Chunks only generate and upload a BAND of that order** (`FOLIAGE_BANDS` = taper floor 0.25 / 0.5 / 1, chosen by `foliageBandToRequest` with `BAND_HEADROOM` 48u): the worker always places the whole chunk (the RNG stream is the only way to reach a blade, and `total`/minY/maxY must not depend on the band), then selects the first `ceil(total × band)` by a bucketed select that reproduces the stable sort's order exactly, so a wider band is a strict SUPERSET PREFIX and widening on approach adds exactly the blades fading in. The sweep re-runs every `SWEEP_STEP` (16u) of travel and widens a chunk once its band would be short within `BAND_WIDEN_MARGIN` (24u; 16 left 26 sweeps short at sprint); widenings share the 4-in-flight budget nearest-first with new chunks, and `instanceCount` is clamped to the held count (short only when outrun: 3 sweeps at 300u/s noclip). A widening REPLACES the chunk's instance buffers (three can't grow a GL buffer), so chunks ahead of the camera's heading are requested for their closest approach (`foliageApproachDistance`) — without that, bands cost +5–10% upload on walks. Measured at a grass spawn (node replay, real worker): startup 77→53MB uploaded, 3.4M→2.3M blades, worker 3.0→1.9s; straight 2400u walk 205→165MB, worker 6.7→4.2s, 37 widenings per 637 new chunks; a turning walk 205→201MB with 68 widenings. Drawn blades verified bit-identical to the pre-band worker at 11 distances × 170 chunks.
- **The lamp-glow grid is dirty-gated** (`markLampGridDirty` in `lighting/lampGlow.ts`; `registerLampHeads`, its disposer and `setLampHeadColor` call it for you): anything that touches `activeLampHeads` by hand MUST call it, or the 64KB grid re-upload skips your change (there's a head-count backstop, but same-count swaps would be missed). Dressing InstancedMeshes get explicit per-chunk `boundingSphere`s and real frustum culling — never set `frustumCulled = false` on a chunk whose bounds are known.
- **Street lamps are INSTANCED dressing** (`objects/dressing/street-lamps`): one draw call + ONE shared material per chunk, no per-lamp components. The per-object street-lamp ACTOR that used to exist alongside it was REMOVED — a second implementation of the same object in the wrong class.
- **Dressing vs actors is a measured perf boundary**: rendering the dressing set (markers, lamps, signals, poles) as per-object spawn components cost ~10–20 fps; instanced chunks recover it. Don't add mass scenery as actors.

### Outrunning the generators (fast-travel collapse)

A player moving faster than generation used to end in single-digit FPS and a minute-long recovery. The cause was never unbounded cache GROWTH (every cache here is radius- or size-evicted) — it was unbounded per-batch WORK plus quadratic per-frame bookkeeping. Five rules keep it from coming back:

- **Catch-up STREAMS, it never settles a debt.** Chunk keys go to the worker sorted nearest-first and are re-sorted against the CURRENT camera position every batch, so ground the player has already left is never generated or mounted at all — rather than generated, mounted, then swept.
- **Generation is TIME-budgeted, not count-limited** (`SPAWN_BUDGET_MS` for spawns, `BUILD_BUDGET_MS` for terrain). Per-chunk cost varies >10× with terrain (a dense city chunk runs the flatten engine over thousands of pad candidates, ~60ms; an empty grassland chunk is nearly free), so any fixed chunk count is both too long in the city and too short in open terrain. The worker returns the chunks it FINISHED (`done`); only those are cached, the rest are re-requested or dropped. `throughput = N / max(N × cost, cadence_floor)`, so budget beyond the floor (`MIN_FRAMES_BETWEEN_BATCHES`) is pure latency.
- **Spawning never waits — not for terrain, not for its own worker.** The pool used to defer to pending LOD1/LOD2 terrain (up to 90 frames — while moving LOD2 is ALWAYS pending, so a sprinting player got one 20-mount batch per ~90 frames) and to await every spawn-worker request before mounting (up to `SPAWN_BUDGET_MS` of new chunks held back points already cached). Both REMOVED: every batch mounts the nearest cached points, at most one worker request fills in the rest (`requestSpawnChunks` / `getCachedSpawnChunks`), and the main-thread ordering is the TaskQueue's priority. MEASURED, interleaved A/B on the same machine and load (headless GPU, camera driven on a fixed path; 'missing' = a flatten-engine building point inside its spawn radius with no built exterior): 300u/s circle through the city, nearest missing building min 17u / 390u → 443u / 485u (5 samples <100u → 0); 45u/s sprint at 6× CPU throttle min 373 / 304 → 516 / 514u; LOD1 never missing under the player in any run. Frame p95 unchanged or better (6× throttle 101.8 / 97.3 → 86.9 / 77.9ms).
- **Terrain overlap queries go through `ChunkIndex`** (`lodSwaps.ts`), a coarse grid bucketed at `LOD5_CHUNK_SIZE` (so any chunk spans ≤ 2×2 tiles). The swap/prune passes ask "does any chunk in set X overlap chunk C?" every frame; scanning the whole set is O(chunks × queue) and outrunning generation grows BOTH sides into the hundreds. `processSwaps` (`LodSwapper`) must still run with no stale chunks — it is what draws freshly built chunks at all; a pass that changed anything, or a fade that ended, keeps the update pass running for one more pass (`swapper.busy`).
- **Terrain heightfields are imperative Rapier bodies, not React** (`generateColliders` in `TerrainRenderer.tsx`): built once per chunk straight into the world and removed in `destroyChunk`. The earlier `<TerrainCollider>` component list needed careful memoization (an unmemoized `args` rebuilt every heightfield on every collider change — ~50 rebuilds per chunk built) and still put ~64 bodies through r-t-r's per-frame body sync plus a whole-list reconcile per build; none of that exists now. Never reintroduce per-chunk `<RigidBody>`s.
- **Caches store their own coordinates.** The client spawn cache, the worker's chunk cache and the despawn ledger all carry world-space centers (and spatial-hash membership) on the entry, because eviction sweeps the whole cache every batch and parsing `"cx_cz"` back out of the key made the one operation keeping them bounded the most expensive thing about them.

## Conventions

- PascalCase for components/types, camelCase for utilities/functions/properties
- SCREAMING_SNAKE_CASE for constants and enums
- **Comments are for what the code cannot say.** Prefer a descriptive name over a comment — if a name needs a comment to be understood, rename it. A comment earns its place ONLY for: a magic value (units, where the number came from, what constrains it); a non-obvious WHY (a rejected alternative and what broke, a measured result, an invariant another file depends on, a hazard the code guards against); or logic that is genuinely confusing on its own. Never restate the next line, narrate history, or duplicate this file — CLAUDE.md is where long-form rationale lives, and a code comment may point here in one line. Section banners only in files long enough to need navigation. When in doubt, cut it.
- **The horizontal plane is x/z, everywhere** — the world is y-up and `y` is always height, including inside 2D code (voronoi, city grid, density placement, chunk offsets): those use `PointXZ` (`utils/math/types.ts`) and `ix/iz`, `dx/dz`, `sx/sz` names, never `THREE.Vector2` or `.y` for a horizontal coordinate. The ONLY `(x, y)` pair is the abstract 2D noise samplers (`simplex2`/`perlin2`/`terrainNoise` in `utils/workers/noise.ts`), whose inputs are not world axes (the road warp feeds them `(z, 0)`)
- **Hierarchy ownership**: DOMAIN → REGION → BIOME is both the content hierarchy and the folder hierarchy — put code at the level it belongs to (biome-specific in the biome folder, and so on up); only genuinely shared code lives outside `world/domains/`
- **Pattern files per folder**: `types.ts`, `constants.ts`, `defaults.ts`, `utils.ts` at the appropriate level — no grab-bag singleton modules (the old `registry.ts` was split this way)
- **Extend, don't duplicate**: every game object extends its CLASS BASE (`objects/actors/Actor.tsx`, `objects/dressing/Dressing.tsx`, `objects/foliage/Foliage.tsx`) plus the shared attribute types (`objects/types.ts`); actor variants spread a base descriptor
- Feature-based directory structure — co-locate assets (shaders, textures) with their biome/feature
- Prefer editing existing files over creating new ones
- Keep biome implementations self-contained; don't add cross-biome dependencies
- Interfaces live in the nearest `types.ts` (world-level types in `src/world/types.ts`)

Rules that came out of building it:
- **Two ids.** `identity` = client uuid in localStorage (persistence key, sent once in `hello`). `id` = server-assigned SESSION id (all presence messages). Two tabs share an identity but are two sessions — that is what makes local two-tab testing possible.
- **Presence is scoped per DOMAIN (rooms), not filtered.** Domain switch = leave(old) + join(new) + fresh `init` to the mover. Phase 6 entity sync must inherit this scoping.
- **Close the socket on `pagehide`.** MEASURED: Chrome leaves a navigated-away page's WebSocket open server-side; without the client closing it, the other tab saw a ghost until the heartbeat reaped it (≤60s) and re-entries inflated the count.
- **Never per-frame React state for network.** Roster changes re-render; movement mutates refs.
- **`move` carries velocity** so receivers extrapolate; a stop is v=0. Drift correction every 250ms only if >0.75u off.
- **Write policy** (`game/persistence.ts`, keyed by IDENTITY — two tabs share one record): saved when the identity's LAST session disconnects IF dirty, else ≤ once/30s if dirty, never on a tick. The client writes through `data:patch` (shallow merge, `PLAYER_DATA_MAX_BYTES` cap, validated in `validatePatch` — where typed keys get checked once the JSON shape exists); the server echoes the merged blob to every session of that identity. `PlayerData`'s shape is still the open placeholder in protocol.ts. Boot REFUSES a stale schema (`DB_AUTO_MIGRATE=1` only for an empty volume's first boot). Order for schema changes: `db:migrate` on the live db (railway ssh), then `deploy`.
- **Windows can't deliver SIGTERM** to a child process — the shutdown flush is unit-tested (`server/test/persistence.test.ts`, on a throwaway SQLite), not by signal.
- The old gh-pages deploy, `homepage`, and `predeploy` are gone; `CNAME` at the repo root is a leftover to delete once DNS points at Railway.

## Entity sync (Phase 6, Sept 2026) — the SERVER runs every actor's state machine

> **Read `NPC_TRACKING.md` first** — the plain-language write-up of how NPCs sync across clients and how to program a new NPC's movement/states (the beeble as the template). This section is the dense reference.

Built on the Phase 2 transport, no new runtime dependencies (esbuild joins the server's DEV deps: the server is BUNDLED because it imports the client's Three-free files from `src/`). Server: `server/src/game/entities/manager.ts` (the simulation + relay) reads the ACTOR CATALOG (`src/objects/actors/catalog.ts` — every `<actor>/spec.ts`: id → stateMachine + body/collider/movement, or a building's hull attrs). Shared: `src/objects/actors/spec.ts` (ActorSpec), `state/runner.ts` (Three-free machine core), `state/motion.ts` + `state/animation.ts` (the two output channels), `state/types.ts`. Client: `src/net/entities/` (entityStore, interpolation, posePlayback, useSyncedEntity), the actor base (`Actor.tsx`), `ModelActor.tsx` (owns the behavior wiring) + `kinematicMover.tsx` + `animationPlayer.ts`, `state/useStateMachine.ts`, `state/useMouseEvents.ts`. Tests: `server/test/{entities,catalog,persistence,physics}.test.ts` (`npm test` in server/ — runs the real beeble machine and a free-moving test kind on the server), `src/objects/actors/state/{motion,animation}.test.ts`.

**Authority: the server, always. No client owns anything, so no player is favored (PvP-fair).** Each registered actor's state machine — THE SAME CONFIG FILE the client has (`beeble/stateMachine.ts`), written once — runs on the server at 10Hz with the NEAREST player in the domain as "the player"; the machine's `ctx.motion` output drives its body on the server physics world and the server publishes changed fields (a stamped pose snapshot, the whole animation-channel state `anim`, state id `sm`, replicated `state`) to the registrants. Every client is placed to match by SNAPSHOT INTERPOLATION (`src/net/entities/interpolation.ts`, pure + unit-tested): every positional update carries the tick's SERVER time `st`; the client keeps the last snapshots per entity and draws it as it was INTERP_DELAY_MS (200ms = 2 ticks) ago on the SERVER clock, interpolating between the two bracketing snapshots — message ARRIVAL time plays no part, so main-thread hitches and bunched packets cannot overshoot, slide or lurch, and a stop lands exactly where/when the server stopped. Rules: past the newest snapshot extrapolate ≤ 250ms then HOLD; a segment much longer than the publish interval is an IDLE GAP = hold at the old pose until one interval before the new one (MEASURED: lerping across the gap hopped ~0.5u the frame the first moving snapshot arrived); consecutive snapshots > 40u apart = a relocation (restart/respawn), no lerp; a per-actor render clock SLEWS (±10%) toward server-time−delay so a re-estimated clock offset never steps the picture. Animation is applied on the SAME delayed clock: the published `anim` state carries its own server-time clocks (`t0`, `pausedAt`, `changedAt`), `animationPlayer.ts` applies it once the render clock reaches `changedAt` and computes the exact clip time from them — so the idle clip starts exactly as the interpolated body reaches the stop, and pause/resume/speed changes land in phase too. This REPLACED (a) the chase/feedforward/0.5u deadzone/6u snap/local-y mover layer and then (b) arrival-time extrapolation eased toward — both produced catch-up hops and slides under real browser load that a headless probe could never reproduce (headless = no hitches). The kinematic mover only PARKS the capsule at the sampled pose so the local player collides with the NPC. `body: "kinematic"` keeps its local gravity/KCC integration ONLY for `serverSynced={false}` actors. NOTE when verifying ANY of this: dotcomma.io runs the last DEPLOYED release — an uncommitted working tree is only ever visible at localhost:3000 (`npm run dev`); a teleport report from production was once misattributed to local changes. ModelActor's runner MIRRORS the server's state id (with the server's motion output injected) so state-keyed visuals (head tracking, sphere-inflate) run where there is a scene. Every mouse INPUT (hover, clicks, scroll — `runner.ts` `mouseActionOf`) is forwarded (`useMouseEvents`, owned by ModelActor) and raised on the server machine's blackboard, gated by the machine's own distance trigger; inputs cross the wire, never triggers. `serverSynced={false}` opts an instance out (purely local, same code path). `serverSynced` is a `GameObjectAttributes` field: actors default true; dressing/foliage default false and have NO implementation (stateless deterministic scenery — nothing to publish; `true` logs a one-time warning).

**THE authoring contract (runner.ts header):** a StateMachineConfig expresses movement/facing through `ctx.motion` (`move(vx,vz)`, `heading(angle,speed)`, `toward(x,z,speed)`, `fly(vy|null)` — null = gravity/ground; for `movement:"free"` null = 0 —, `stop()`, `face(yaw)`, `faceHeading()`, `faceToward`, `turnToward(x,z,maxStep)`, reads `yaw`/`angleTo`) and animation through the state's `animation: { clip, loop?: "repeat"|"once", speed? }` shorthand or `ctx.animation` (`play/pause/resume/stop/setSpeed`), and never the scene for those; anything scene-bound (bones, geometry) must guard on `ctx.groupRef.current` (null on the server); a PER-PLAYER effect (sound, dialog) is `if (ctx.groupRef.current && ctx.input.leftClick)` in the state the click lands in — mirror flags are this player's only — while the state it transitions INTO runs on every client; no Three at RUNTIME in a config (`import type`). The server's simulation time is TICK-based (`elapsed += dt`), so `stateElapsed` agrees with `delta` exactly as on the client. Adding a synced NPC = `stateMachine.ts` (transitions hold trigger OBJECTS — the runner collects them and throws on an unknown trigger id/target outside production) + `spec.ts` (id, stateMachine, `body: "kinematic"`, `collider`, `movement: "ground" | "free"`, model + spawn attrs) + one catalog line + a `{ actor: SPEC }` entry in a biome spec's `actors` — no component, no actor.tsx, no server file. The server's input reach check is `serverInteractReachSq(spec)` = (`interactReach` ?? 5, the client raycast's reach) + 3u slack. `movement: "free"` is a `FreeBody` on the server (velocity integrated, no gravity/ground/holds) and the mover's free branch on the client. `dynamic` (pushables) is NOT implemented.
